Source: [[docs/superpowers/specs/2026-08-31-sr-code-validation-traceability-design#canonical-relations|SR code and validation traceability design — canonical relations]].

This SR is distinct from [[SR-001]]: SR-001 requires lifecycle navigation; this SR requires
implementation-time maintenance and independent per-SR review of the production and validation
relations that make that navigation truthful. It complements [[SR-023]], which computes
import-overlap coverage, and [[SR-049]], which enforces produced-code traceability through gates.

**AC-1 became `test_marker`-backed (2026-09-03).** `coherence.register.relations.resolve_sr_relations`
now resolves the structured `implemented_by`/`verified_by` relations this design names
(`path`/`symbol`/`test` entries) against the real repository: paths are root-confined with the
same `candidate.is_absolute() or ".." in candidate.parts` convention already used by
`coherence.navigate.snapshots` and `coherence.policy.compiler`, and symbol/pytest-node identifiers
are resolved against the existing code map (`substrate.codemap.store.ensure_fresh` +
`substrate.codemap.build.file_signatures`) rather than a second parser -- no line number is ever
accepted as identity, and a repeated `(field, path, symbol-or-test)` declaration is rejected as a
duplicate rather than silently accepted twice. `coherence.trace.model.edges_from_frontmatter` now
tells the two `verified_by` shapes (this structured relation vs. the pre-existing string-list
SR-to-task/run graph edge) apart by each entry's own shape rather than by node kind, so the legacy
edge keeps working on SR nodes that still use it. `tests/unit/coherence/register/test_relations.py`
binds this AC via `@pytest.mark.sr("SR-050")`.

This landed via a background workflow whose own review stage produced a false "rejected" verdict
— it reported no implementation existed anywhere, based on an investigation that only checked
`git diff` (which does not show untracked new files) and appears to have run against a stale or
mid-write state after a network failure. Independently re-verified from scratch before trusting
either side: read every file directly, confirmed the resolver reuses the code map, confirmed the
`verified_by` fix uses per-entry shape detection (not the node-kind gate the review claimed), and
reran every test myself. One real gap the review did *not* correctly identify but existed
nonetheless — duplicate-relation detection, required by this AC's own source plan — was found by
reading the code directly and fixed the same way (TDD, tests added first).

**AC-3 was narrowed on review (2026-09-02).** It originally named a specific, not-yet-existing
actor — "an agent's relation-review verdict" — as the thing being gated. That producer does not
exist: AC-1 and AC-2 (the structural/fidelity reviewer that would emit such a verdict) remain
`manual` because no reviewer exists in `src/coherence` today. What the AC's substance actually
requires — a gate that only closes on an attributed, correctly-scoped human `accept` decision,
fail-closed on everything else (missing, mis-scoped, unattributed, rejected, or deferred) — is
exactly what `_human_review_obligation` (`src/coherence/policy/compiler.py`) already implements
and what `tests/unit/coherence/policy/test_compiler.py` already exercises exhaustively (missing
decision, wrong-SR scope, wrong `gate_id`, reject, defer, blank/whitespace `decided_by`). AC-3 now
binds to that existing, already-tested mechanism via `@pytest.mark.sr("SR-050")` on six of those
tests. Once AC-1/AC-2's reviewer is built, it must route its verdict through this same
`review:<sr_id>` gate rather than a parallel closure path — that wiring is future work, tracked by
AC-1/AC-2 staying manual.

**AC-2 split into AC-2/AC-4 on review (2026-09-03).** The source design (§ Review agents) names
three distinct reviewers, not two: a **structural trace reviewer** and an **evidence
reconciliation reviewer**, both fully deterministic (relation syntax, path/symbol/test-node
resolution, duplicate declarations, manifest/validation-output reconciliation — graph and file
facts, no judgement involved), and a **fidelity reviewer**, which is not (it judges whether a
link genuinely substantiates a claim). The original AC-2 merged all three into one criterion and
justified all of it as `manual` for the same reason — that reading did not distinguish "manual
because unbuilt, becomes a bare test the moment it exists" (structural, evidence integrity) from
"manual because it is inherently a judgement call, and always will need one" (fidelity). Splitting
makes each criterion's verification story honest: AC-2 now covers only the two deterministic
reviewers and states plainly it needs zero agent or human judgement once built; AC-4 covers only
fidelity, is explicit that the *judgement* stays a model/human call by nature, and ties its
*enforcement* to AC-3's already-built, already-tested gate rather than inventing a second,
parallel closure path — the same "agent proposes, gate enforces attributed human consent, nothing
closes silently" pattern AC-3 already proves works. This also answers a related, corpus-wide
finding raised at the same time: `_human_review_obligation`'s compiled requiredness is
`not_applicable` outside `high_assurance` (`src/coherence/policy/compiler.py`), so under this
repo's own default profile a `manual` criterion's human review is not merely easy to skip — the
system does not require it at all. That gap is not specific to SR-050 or to AC-4; it is tracked as
its own requirement, [[SR-059]], rather than patched here.

**AC-2 became `test_marker`-backed (2026-09-03).** `coherence.register.review` now implements
both deterministic reviewers the source design names (§ Review agents) and the AC-2 split above
scoped to: a **structural trace reviewer**, `structural_review(root, req) -> StructuralReview`,
which reuses `coherence.register.relations.resolve_sr_relations` (AC-1's own resolver) for
malformed/out_of_scope/dangling/duplicate findings and adds the one category that resolver does
not cover — a bound SR declaring zero `implemented_by` or zero `verified_by` entries is `missing`
— plus a register-wide `unaccounted_changed_files(root, reqs, manifests)` for changed files (read
from every evidence run manifest's `implementation.changed_files`, never `git diff`/`git log`,
per the source plan's own instruction) that no SR anywhere declares a relation to; and an
**evidence reconciliation reviewer**, `evidence_reconciliation_review(root, req, manifests) ->
ReconciliationReview`, which partitions declared-vs-changed and declared-vs-executed facts into
exactly the six categories the design names (`declared_and_changed`, `declared_but_not_changed`,
`changed_but_undeclared`, `declared_and_executed`, `executed_but_unlinked`,
`linked_but_stale_or_failed`), with every operational definition — what "executed" and "stale or
failed" mean, and the judgement call of scoping "changed" to manifests that carry a validation
entry for the SR rather than the whole evidence store — spelled out in the module's own
docstrings. `StructuralReview` and `ReconciliationReview` are two structurally separate
dataclasses, never one merged verdict, satisfying AC-2's own "never merged into one verdict"
clause; `coherence register review <SR-ID>|--all` (`src/coherence/register/cli.py`) prints them
as two distinct top-level JSON keys, `structural` and `evidence_reconciliation`. Neither reviewer
touches `src/coherence/policy/compiler.py`'s obligation system or gates anything — both are
read-only reporting, exactly as the source plan's T4 work package requires ("Register it as a
blocking governed obligation" is a later, separate work package, T7); the fidelity reviewer that
AC-4 names remains unbuilt and `manual`, unaffected by this change.
`tests/unit/coherence/register/test_review.py` binds this AC via `@pytest.mark.sr("SR-050")`, with
one fixture per finding class
for both reviewers, including the plan's own explicit fixtures — a changed file with no SR link
anywhere (`unaccounted`) and a `verified_by` link to a deleted test node (`dangling`) — plus a
CLI-level test that a single dangling relation surfaces on the structural side only, never folded
into the evidence-reconciliation output.

**AC-2's review gaps closed (2026-09-03).** Code review found three gaps in the initial
`coherence.register.review` implementation above, all now fixed with tests added first:

1. `unaccounted_changed_files` covered only the "changed production files" half of AC-2's own
   criterion text — an executed test that was never itself modified had no code path that could
   ever flag it, even though the criterion names "changed production files **or executed tests**
   with no owning SR relation" as one thing. `_executed_test_paths` now reads the pytest node ids
   this repository's evidence writers actually record (`validation[*].requirements[*].tests` and
   `acceptance[*].tests` — the manifest schema types `validation` as an untyped `array of object`
   with no canonical field name, but every manifest under `evidence/runs/` uses one or both of
   these), and `unaccounted_changed_files` now reports an executed test file with no owning SR
   relation the same way it already reported an unaccounted changed file.
2. `linked_but_stale_or_failed`'s "stale" branch only fired when an SR had *never* been validated
   by any manifest — evidence that was valid once but went out of date (the linked file changed
   again after the last passing validation, with no re-validation recorded since) silently passed
   as clean. `evidence_reconciliation_review` now compares, by manifest recency (`ended_at`
   falling back to `started_at`, compared lexicographically since both are ISO-8601), the most
   recent manifest that changed one of the SR's linked (`verified_by`) paths against the most
   recent manifest that recorded *any* validation entry for the SR; a linked path changed after
   the last recorded validation is reported as genuinely stale. Manifests carrying neither
   timestamp field are never treated as "after" any other manifest, so recency-blind callers get
   no stale findings rather than an unreliable guess.
3. The `missing` structural finding's non-second-guessing of legacy plain-string `verified_by`
   entries (documented above as a deliberate choice) went further than intended: a bound SR with
   zero structured relations under a field could permanently defeat `missing` there forever by
   keeping any legacy string entry, even one written long before this AC existed, leaving a
   canonically-unreviewable field that looked structurally clean. `missing` now requires at least
   one *structured* (dict-shaped) entry per field — a field mixing a legacy string with a
   structured entry is still not `missing` (only the structured entries count, and one is
   enough), but a field holding only legacy strings now is.

`tests/unit/coherence/register/test_review.py` gained one fixture per gap (an executed-but
-unchanged orphan test; a legacy-only `verified_by` field on an otherwise-complete SR; a linked
path changed again after its last recorded validation, with no re-validation for that SR since).

**AC-4's fidelity reviewer landed (2026-09-03, SR-050 T5).** `coherence.register.fidelity_packet`
(packet builder), `coherence.register.fidelity_findings` (schema + construction-time validation),
`coherence.register.fidelity` (`review_fidelity` plus a real `PiAgentBackend`-dispatch default
judge under the new `AgentRole.FIDELITY_REVIEW`), and `coherence.register.fidelity_persistence`
(`review-findings/fidelity/<sr_id>.json`, with re-run disposition tracking against `review:<sr_id>`
accept decisions) now implement the fidelity reviewer this AC names, wired into
`coherence register review --fidelity` (a third top-level JSON key, never merged with AC-2's two)
and `--check` (the CI-gate mode below). AC-4 stays `kind: manual` regardless — see this AC's own
`reason` above for exactly why one criterion combining a judgement clause and a mechanical clause
cannot honestly split its verification kind, and exactly which existing AC-3 tests already cover
the mechanical half.

The design spec's stronger claim — "for `high_assurance` work, unresolved fidelity findings
block" — is distinct from AC-4's own text (which only requires routing through AC-3's gate) and is
realized through a *different*, deliberately separate mechanism: `coherence register review
--fidelity --check`, wired into `.factory/factory.yaml`'s `full` gate, exits non-zero only when a
`high_assurance`-profile SR carries an `open` (not `escalated`, not `dispositioned`) fidelity
finding; under every other profile it exits 0 regardless, and findings are still recorded/printed,
just not CI-blocking. The profile-conditional logic lives entirely inside the command itself —
`_ci_verification_obligation` (`src/coherence/policy/compiler.py`) is reused completely unmodified,
exactly as the plan specified, since it already treats every configured gate command as
unconditionally blocking. This CI gate is a blocking *check*, not a requirement-closing mechanism —
it can fail a build; it cannot satisfy `ob:human_review:sr:<id>`, which remains AC-3's alone.

Two of the source plan's open design questions were resolved explicitly rather than left open:
`_human_review_obligation`'s `reason`/`resolve_cmd` strings are deliberately left untouched by this
task (fidelity-report visibility for a human resolving that obligation lives in the CLI output
only; `src/coherence/policy/compiler.py` is not modified anywhere in T5); and `missing_link_compound`
is inapplicable to a legacy SR carrying no `acceptance:` block (only `overstated_link`/
`incidental_helper`/`weaker_subset_test`/`different_behavior` can fire for such an SR) — there is no
"compound" claim to check partial coverage of without a declared acceptance-criteria list. This is
not merely a documented convention: `coherence.register.fidelity_findings.build_finding` mechanically
rejects a `missing_link_compound` candidate whenever `packet.acceptance == ()`, raising
`FidelityFindingError` before it can become a finding (see
`tests/unit/coherence/register/test_fidelity_findings.py::
test_missing_link_compound_is_rejected_for_a_packet_with_no_acceptance`), and the judge-facing
`.pi/skills/fidelity-review/SKILL.md` prompt says so explicitly under the `missing_link_compound`
bullet.

**This SR declared its own relations (2026-09-04).** Until now SR-050 required every implementation
slice to maintain canonical `implemented_by`/`verified_by` relations while declaring none of its
own — its AC-1 obligation applied to every requirement except the one that states it. The
`implemented_by`/`verified_by` blocks above close that, naming the resolver, both deterministic
reviewers, the four fidelity modules, the judge dispatcher, and `_human_review_obligation` (AC-3's
actual mechanism), plus the test files that verify them. This was forced, not optional:
[[SR-049]]'s claim reconciliation reports every path a commit claimed for an SR that the SR
declares no relation to as a blocking gate finding, so an undeclared SR-050 would have failed the
`full` gate the moment any commit claimed it.

**AC-1's resolver gained a file-only `implemented_by` shape (2026-09-04).** `implemented_by`
previously required a `symbol` on every entry, which made a produced artifact that is not Python
source — a gate config, a JSON schema, a hook script — impossible to declare at all, while
[[SR-049]]'s gate still reported it as claimed-but-undeclared. `resolve_sr_relations` now accepts
a file-only `implemented_by` entry when the path's suffix is not `.py`, mirroring the file-only
`verified_by` allowance this resolver already made for non-pytest harnesses. The carve-out is
scoped by suffix deliberately, so this AC keeps its teeth exactly where a symbol always exists:
a `.py` entry with no symbol is still a `missing required 'symbol'` issue, asserted directly by
`test_a_python_implemented_by_entry_still_requires_its_symbol`.

**AC-5's relation-maintenance obligation landed (2026-09-04, SR-050 T3).**
`coherence.policy.compiler._relation_maintenance_obligation` (new `relation_maintenance` Obligation
kind, `task:*` scope) reconciles a task's own `satisfies` SRs' declared `implemented_by`/
`verified_by` relations against a caller-supplied changed-files list, filtered to real
production/validation code via the new `substrate.codemap.build.is_source_path` -- scoped to only
the task's own SRs (register-wide reconciliation against any SR is SR-057/058's already-built
`unaccounted_changed_files`, not duplicated here). `factory.preflight.checks.
run_completion_preflight` -- the function `factory/orchestrator/runner.py` already consults to
decide whether a completed run's outcome stands -- now calls this obligation and raises a new
`BLOCKING` `relation_uncovered` issue when it reports `open`, escalating the run back to `todo`
exactly like every pre-existing check in that function. The runner supplies the changed-files list
via `GitOps.changed_files(repo_root, start_commit)`, the same call the evidence manifest's own
`implementation.changed_files` will make moments later -- not a second, divergent way of asking
"what changed."

Deliberately unresolved by this AC, tracked separately: whether `run_completion_preflight`'s other
four checks (`validation_missing`/`validation_failed`/`validation_stale`/`review_missing`/
`must_fix_unresolved`) should ever be migrated onto `compile_obligations` too ([[SR-063]]); no
performance budget for this or any other FEAT-001 review mechanism ([[SR-064]]).

**AC-2's `unaccounted` bucket now honours the claim exemptions (2026-09-04).** The register-wide
bucket unioned `implementation.changed_files` across every manifest with no filter, which was
correct while the only manifests were orchestrated task runs — their changed files *are* the
task's produced code. [[SR-049]]'s commit ingestion broke that assumption: an ingestion manifest's
`changed_files` is the union of every commit in its range, so the first real ingestion added four
findings naming `requirements/SR-049.md`, `requirements/SR-050.md`, a plan document, and a skill
prompt. None of them could ever be cleared — no requirement declares its own `.md` file as an
implementation of itself — so the bucket would have grown by every doc commit forever while
staying permanently uncloseable. `unaccounted_changed_files` now skips a changed path matching a
`.factory/trace-claims.yaml` exemption glob, which is the same list and the same reason as the
claim denominator's own filter, and is faithful to this AC's wording: an exempt path is not a
changed *production* file. Executed tests are deliberately not filtered — a test that ran is a
validation artifact whichever glob its path matches. Measured on this repository: 21 findings
before adoption, 25 with the first ingestion manifest and no filter, 21 with it.

**T3's own relations were declared (2026-09-04).** AC-5's slice landed with its mechanism
undeclared: `substrate.codemap.build.is_source_path`, `factory.preflight.checks.
run_completion_preflight`, `factory.orchestrator.runner.run_next` and their three test files
changed with no `implemented_by`/`verified_by` entry on any requirement, so [[SR-049]]'s first live
ingestion reported all six as `unaccounted`. The irony is the point: AC-5 is the criterion that
blocks a task from completing when its changed code is undeclared, and it shipped undeclared —
which is exactly the failure it exists to catch, missed because the six commits carried no `SR:`
trailer (they were written before the hook was enabled, so nothing claimed them and only the
register-wide bucket saw them). The entries above close it, and the twelve T3 tests now carry
`@pytest.mark.sr("SR-050")` so the files declared as verifying this SR actually say so.

One relation is coarser than it reads and is recorded here rather than left to be rediscovered:
`factory.orchestrator.runner:run_next` implements the whole orchestrator run loop, and AC-5's share
of it is a single argument — `changed_files=git_ops.changed_files(repo_root, start_commit)` — passed
into the completion preflight. `run_next` is the smallest symbol that contains that call site, so
it is the honest target at the granularity `path`/`symbol` offers, but the link claims
participation, not ownership: this is the kind of link AC-4's fidelity reviewer would rightly flag
as `overstated` if it were read as "run_next exists to implement SR-050".
