Source: [[docs/superpowers/specs/2026-09-03-typed-relation-wikilink-mirroring-seed|Typed-relation wikilink mirroring across artifact families — seed]].

Discovered during [[SR-003]]'s authoring-consent decision (2026-09-03): the human asked whether a
spec should be required to have at least one covering requirement, mirrored as a wikilink the way
[[SR-001]]/AC-3 already requires for a requirement's own `upstream` field. It doesn't — and the
gap runs deeper than one missing check. `missing_upstream_wikilinks()` only reads a requirement's
`upstream` field; `spec_ref` edges (the only relation touching a `spec:` node today) are built
exclusively from a plan's frontmatter/body, never from a requirement; and `trace/gaps.py` has
`plan_no_spec` (a plan must reference a spec) but nothing in the reverse direction. This SR is
about closing that direction, generalizing [[SR-001]]'s existing mirror mechanism rather than
inventing a parallel one.

**Acceptance criteria added on review (2026-09-03).** Earlier registered with zero ACs on the
reasoning "deliberately not designed yet" — challenged on review: not having chosen an
implementation detail (the exact frontmatter field name, the new `GapKind`'s exact name) is not a
reason to avoid stating a testable behavioral claim, any more than it was for [[SR-050]]/AC-1
earlier this session, which named a concrete criterion before `implemented_by`/`verified_by`
existed. AC-1/AC-2 above state the observable contract without committing to the field name or
`GapKind` name, both `manual` and honestly reasoned as unimplemented. What remains a genuine open
design question, not stated as an AC: whether the generalization reaches beyond specs to other
artifact families (SR-to-SR, SR-to-FEAT — see the confirmed case below). [[SR-001]]'s own AC-3
narrowing note anticipated needing this broader vocabulary and originally (wrongly) cited
[[SR-056]] for it; that citation is corrected to this SR.

**Confirmed beyond specs (2026-09-03), while presenting [[SR-004]]:** answering whether FEAT-001
depends on [[SR-023]] surfaced a real instance of exactly this gap outside the spec case. SR-050's
own governing design
([[docs/superpowers/specs/2026-08-31-sr-code-validation-traceability-design]]) and its plan
explicitly declare SR-050 reuses [[SR-023]] (FEAT-007) and extends [[SR-049]] (FEAT-013) — real,
source-documented cross-FEAT dependencies — yet neither appears as a typed relation anywhere;
[[SR-050]]'s and [[SR-023]]'s `upstream` fields are both empty, and the only trace is prose in a
separate design doc, not the requirement files themselves. This is no longer a hypothetical: "other
artifact families" should include SR-to-SR and SR-to-FEAT prose references, not only specs, when
this SR is designed.

**AC-1 became `test_marker`-backed (2026-09-04).** A new `relates_to: [id, ...]` field on
`Requirement` (`src/coherence/register/register.py`, parsed in `parse_requirement` exactly like
`upstream` -- scalar-or-list coercion, `str()`-cast entries, defaults to `[]`) is the typed
relation this AC needed: a flat list of ids from any artifact family, read literally with no
per-kind transform -- a bare `SR-NNN`/`FEAT-NNN` id (matching that node's own trace-graph id
exactly) or a `spec:<id>`-prefixed id (matching a canonical spec node's `spec:<id>` id, per
`coherence.trace.model._frontmatter_spec_node`). `upstream` itself is completely unchanged: same
field, same type, same parsing, same SR-001/AC-3 requirement-to-requirement scope -- this SR adds
a second, independent field, it does not repurpose the first.

The wikilink-mirror check is generalized, not duplicated: `missing_upstream_wikilinks`'s matching
logic (plain `[[id]]` and pipe-alias `[[id|...]]` forms, declared-order dedup) is extracted
verbatim into a private `_missing_wikilinks(ids, body)` helper; `missing_upstream_wikilinks` now
calls it with `req.upstream` and is otherwise byte-identical in behavior and signature (regression
tests re-run unchanged). Two new functions reuse that same helper: `missing_relates_to_wikilinks`
checks `req.relates_to` alone, and `missing_relation_wikilinks` checks `req.upstream` and
`req.relates_to` together (deduplicated across both fields), which is what this AC's criterion
text actually describes -- one check, both fields, "the same way upstream is already checked."
`tests/unit/requirements/test_register.py` binds this AC via `@pytest.mark.sr("SR-057")`, alongside
the pre-existing `missing_upstream_wikilinks` tests (also re-run, unmodified, as regression
coverage).

One scoping judgment call, named honestly: for a spec target, the literal `relates_to`/mirror
string this AC requires (`spec:<frontmatter-id>`) does not match how this repo's bodies actually
wikilink specs today (a relative file path, e.g. this very requirement's own
`[[docs/superpowers/specs/2026-09-03-typed-relation-wikilink-mirroring-seed|...]]` link above) --
Obsidian will not resolve a literal `[[spec:some-id]]` link to a real file. AC-1's text only
requires "mirrored as a wikilink," not "is Obsidian-navigable," so this is accepted as a known,
unresolved friction rather than silently designed around; a future SR could reconcile the spec
node id with its wikilink-navigable form, but that is out of this SR's scope.

**AC-2 became `test_marker`-backed (2026-09-04).** A new `GapKind`, `artifact_uncovered`, mirrors
`plan_no_spec`'s exact shape in `trace/gaps.py`'s `find_gaps()`: for every node whose kind is
`spec`, `sr`, or `feat`, if no edge of kind `relates_to` targets it, one `artifact_uncovered` gap
is added, with the same `_disposition_of` exempt/deferred handling every other gap kind already
gets (an SR still cannot exempt itself, per spec 4.4, since `_disposition_of` never treats `sr`/`br`
as exemptable). The `relates_to` edges themselves come from `coherence.trace.model`: a new
`relates_to` `EdgeKind`, and `extract_edges` reads `meta.get("relates_to")` on `sr`-kind nodes only
(the field lives on a requirement's frontmatter per this SR's approved design; a task or `br`
carrying the same key produces no edge), with the same literal-id, no-transform reading `upstream`
already uses.

**Design decision, written out per the task brief's own prompt: does `upstream` also count as
coverage for the SR-to-SR case? No -- only `relates_to` does.** A requirement's `upstream` lists
its OWN prerequisites ("what I depend on," pointing from the dependent SR toward the one it needs);
"is this SR covered" is a different, reversed question ("does anything reference me"). Folding
`upstream` into the coverage check would (a) blur the boundary SR-001/AC-3 already drew around
`upstream` staying requirement-to-requirement-dependency-only, entangling a scoping decision that
requirement explicitly made with a new one this SR makes; (b) still leave every spec and FEAT node
uncovered by definition, since `upstream` can never reference either kind, so it would only give
inconsistent, kind-dependent coverage semantics; and (c) risk manufacturing false "covered" readings
for pairs that merely happen to share a dependency edge for unrelated reasons. `relates_to` is the
one field this SR gives an explicit "this artifact is covered" meaning (AC-1's own criterion text:
"an id a requirement declares as a spec it covers"), so it is the only channel `artifact_uncovered`
honors -- confirmed by a dedicated regression test
(`test_an_upstream_edge_alone_does_not_satisfy_artifact_uncovered`) that an `upstream` edge alone
leaves the target still uncovered.

`tests/unit/trace/test_gaps.py` binds this AC via `@pytest.mark.sr("SR-057")`, with one fixture
per node kind (spec/SR/FEAT) crossed with covered/uncovered, plus the `upstream`-does-not-count
regression above and a fixture confirming `task`/`plan` nodes never gain this gap kind (scoped to
spec/sr/feat only, as AC-2's own text names). `tests/unit/trace/test_model_edges.py` separately
covers the new `relates_to` edge extraction (present for `sr`, absent for `task`) via
`@pytest.mark.sr("SR-057")`.

Landing this surfaced three existing fixtures written before `artifact_uncovered` existed, each
now newly and correctly flagged: two CLI-gate tests (`tests/unit/trace/test_cli_check.py`) whose
plan-referenced test spec had no requirement covering it, and one status-precedence test
(`tests/unit/coherence/test_status.py`) whose bare `FEAT-001` fixture had none either. All three
were about unrelated mechanics (task exempt/defer, and audit-age precedence, respectively), not
spec/FEAT coverage, so each fixture's incidental spec/FEAT node was marked `trace_exempt: true` to
keep testing what it always tested -- not to suppress the gap generally, since none of these
fixtures depends on `artifact_uncovered` being silent elsewhere. No other test in
`tests/unit/coherence`, `tests/unit/requirements`, or `tests/unit/trace` needed a change; this was
found only by running those broader suites, not the narrow required list -- the same lesson
[[SR-050]]'s own AC-1 landing note records from its own review episode.

Running `tests/unit/system` (wider still, not in this SR's own required list, checked anyway for
the same reason) surfaced one more real gap this way: `coherence.navigate.remediation.REMEDIATION`
is an exhaustive `GapKind -> {headline, command, ...}` map the system navigator's UI renders
directly, and `tests/unit/system/test_remediation.py::test_every_gap_kind_has_an_entry` asserts
every `GapKind` has one. `artifact_uncovered` now has an entry there too, following `sr_unsatisfied`'s
precedent (not `plan_no_spec`'s): both are reverse-direction gaps -- something ELSE must declare
the missing edge, not the flagged node itself -- so both point at `/trace-fix {id}` (`command_kind:
slash`) rather than a direct `coherence.trace link` shell flag, since no `--relates-to` link flag
exists (adding one is out of this SR's scope: AC-1/AC-2 never require a write path, only the field,
the check, and the gap). Two more `tests/unit/system` failures were investigated and confirmed
pre-existing, unrelated to this SR (reproduced identically on `git stash` before any of these
changes): `test_every_shell_command_names_a_real_subparser` (an unrelated stale
`factory.validation`-module command predating this SR) and, in `tests/unit/validation`, one
validation-report-schema test -- neither touched.
