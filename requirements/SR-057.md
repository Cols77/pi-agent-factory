Source: [[docs/superpowers/specs/2026-09-03-typed-relation-wikilink-mirroring-seed|Typed-relation wikilink mirroring across artifact families — seed]].

Discovered during [[SR-003]]'s authoring-consent decision (2026-09-03): the human asked whether a
spec should be required to have at least one covering requirement, mirrored as a wikilink the way
[[SR-001]]/AC-3 already requires for a requirement's own `upstream` field. It doesn't — and the
gap runs deeper than one missing check. `missing_upstream_wikilinks()` only reads a requirement's
`upstream` field; `spec_ref` edges (the only relation touching a `spec:` node today) are built
exclusively from a plan's frontmatter/body, never from a requirement; and `trace/gaps.py` has
`plan_no_spec` (a plan must reference a spec) but nothing in the reverse direction. This SR is
about closing that direction, generalizing [[SR-001]]'s existing mirror mechanism rather than
inventing a parallel one.

**Acceptance criteria added on review (2026-09-03).** Earlier registered with zero ACs on the
reasoning "deliberately not designed yet" — challenged on review: not having chosen an
implementation detail (the exact frontmatter field name, the new `GapKind`'s exact name) is not a
reason to avoid stating a testable behavioral claim, any more than it was for [[SR-050]]/AC-1
earlier this session, which named a concrete criterion before `implemented_by`/`verified_by`
existed. AC-1/AC-2 above state the observable contract without committing to the field name or
`GapKind` name, both `manual` and honestly reasoned as unimplemented. What remains a genuine open
design question, not stated as an AC: whether the generalization reaches beyond specs to other
artifact families (SR-to-SR, SR-to-FEAT — see the confirmed case below). [[SR-001]]'s own AC-3
narrowing note anticipated needing this broader vocabulary and originally (wrongly) cited
[[SR-056]] for it; that citation is corrected to this SR.

**Confirmed beyond specs (2026-09-03), while presenting [[SR-004]]:** answering whether FEAT-001
depends on [[SR-023]] surfaced a real instance of exactly this gap outside the spec case. SR-050's
own governing design
([[docs/superpowers/specs/2026-08-31-sr-code-validation-traceability-design]]) and its plan
explicitly declare SR-050 reuses [[SR-023]] (FEAT-007) and extends [[SR-049]] (FEAT-013) — real,
source-documented cross-FEAT dependencies — yet neither appears as a typed relation anywhere;
[[SR-050]]'s and [[SR-023]]'s `upstream` fields are both empty, and the only trace is prose in a
separate design doc, not the requirement files themselves. This is no longer a hypothetical: "other
artifact families" should include SR-to-SR and SR-to-FEAT prose references, not only specs, when
this SR is designed.
