**Bound 2026-09-04** by the commit-claim traceability slice designed in
[[docs/superpowers/specs/2026-09-04-commit-claim-traceability-design|Commit-claim traceability — design]]
and planned in
[[docs/superpowers/plans/2026-09-04-commit-claim-traceability-plan|its implementation plan]].
Until then this requirement was `proposed` and unbound, with no acceptance criteria at all.

## What the mechanism is

A commit records one fact nothing else in the system holds: **which requirement the work was done
in service of.** Everything a traceability review otherwise needs — which files changed, which
symbols they contain, whether a path is production or validation — is already derivable from the
diff, the code map, and the requirement's own frontmatter. So the trailer declares intent
attribution and nothing more:

```
SR: SR-050, SR-023
```

Commits are an **input consumed at a checkpoint, never a durable ledger.** Any
`coherence register review` or `full` gate run ingests the commit range since the newest manifest
and writes what it learned into a new evidence manifest; from that moment the manifest is
authoritative and the commits no longer matter. This is why no workflow has to be forbidden:
rewriting before ingestion is harmless because nothing depended on the commits yet, and rewriting
after ingestion cannot lose anything because the manifest retains the per-commit detail. AC-2's
last clause asserts that directly, against a real squash that orphans the ingested shas — the
design named this the load-bearing test of the checkpoint model, and it was the one fixture the
first implementation pass did not write.

**No reviewer reads git.** `coherence.register.review.unaccounted_changed_files` documents the
constraint that changed files come from evidence manifests, never `git diff`/`git log`, and that
constraint is preserved exactly: git is consumed once, at ingestion, into the manifest. Git became
an input to the evidence store, never an authority the review layer consults.

## How this relates to [[SR-050]]

[[SR-050]] owns the relation schema and the per-SR review contract; this requirement owns the
attribution input and the gate. Concretely, the claim denominator re-bases [[SR-050]]/AC-2's
existing `evidence_reconciliation_review` onto a correct denominator without adding a finding
taxonomy: `changed_but_undeclared` stops meaning "changed in some manifest that happened to
validate this SR" and starts meaning "a commit explicitly claimed this SR and touched this file,
which this SR declares no relation to". [[SR-050]]/AC-2's own criterion text is unchanged, and
[[SR-050]]/AC-4's fidelity packet gains claim facts while staying `kind: manual`. Those changes are
declared by [[SR-050]], not here; this requirement declares only the claim mechanism itself and the
gate over it.

## Why these markers are on SR-049 and not SR-054

A new requirement for commit-level attribution (candidate "SR-062") was proposed and **declined**
at [[SR-044]] consent on 2026-09-04; no requirement was authored. The 25 tests were then parked on
[[SR-054]], and that commit's own message recorded the two reasons it was wrong: [[SR-054]]'s
statement is scoped to *"every FEAT-017 implementation task"*, so it does not describe a commit
made **outside** a governed task — exactly the case this mechanism handles — and [[SR-054]] is
still `proposed` with no binding and no acceptance criteria, so the markers named a real
requirement while closing nothing.

SR-049 is the right home and needs no new consent, because it is already in the register and its
statement is precisely about produced artifacts carrying gate-validated relations to their owning
SR. Binding it here adds acceptance criteria to an existing, already-consented requirement; it
does not author a new one, so the declined consent is not being routed around.

## Two fixes this binding forced, and why they were not cosmetic

Writing honest criteria surfaced two defects that made AC-3's gate **unsatisfiable**, not merely
noisy. Both are fixed with tests written first:

1. **Exempted paths leaked into the claim denominator.** `claimed_paths` collected every
   `changed_files` entry of a claiming commit, including the paths that same commit had recorded
   as exemption-matched. Since the exempt list's whole meaning is "a change here never requires a
   declared relation", every commit touching a doc alongside code produced a permanent
   `changed_but_undeclared` finding that no declaration could ever clear — and that finding is
   exactly what the blocking gate fails on. The exempt list had been wired into the commit-time
   check alone and had no effect on the denominator it exists to shrink.
2. **A non-Python produced artifact could never be declared.** `implemented_by` required a
   `symbol`, so a gate config, a JSON schema, or a hook script — all genuinely produced
   implementation artifacts — had no declarable shape, while the claim gate still reported them as
   claimed-but-undeclared. `coherence.register.relations` now accepts a file-only `implemented_by`
   entry when the path is not a `.py` file, mirroring the file-only `verified_by` allowance
   [[SR-050]]/AC-1's resolver already made for non-pytest harnesses. The carve-out is scoped by
   suffix so Python source — the one place a symbol always exists — still must name it. Widening a
   path-scoped exemption list instead was rejected: the design already warns that the exempt list
   is frictionless and therefore grows until it covers everything inconvenient, which is why the
   review reports a per-glob exemption count at all.

## Deliberately not built, and not claimed by any AC above

* **The `core.hooksPath` gate assertion.** The design proposed that the `full` gate assert
  `core.hooksPath` is set, so a missing hook becomes a gate failure rather than an invisible gap on
  one machine. It was never built, and no AC here claims it. The hook remains fast feedback only —
  per-clone, never cloned with the repository, and bypassed by `--no-verify` by design — with
  enforcement living entirely in AC-3's ingestion-time gate, where the commits already exist and
  nothing can be skipped.

* **The epoch as a per-path filter.** The design describes claim-based findings firing only for
  files touched after the epoch commit. What is implemented is coarser and honest about it: `epoch`
  bounds *which commits are ingested at all* (AC-2), and the reconciliation then switches
  denominators all-or-nothing per review via `any_claims` rather than filtering path by path. The
  fallback is deliberately all-or-nothing rather than per manifest, because mixing a claim
  denominator with a scoping heuristic in one verdict would make `changed_but_undeclared` mean two
  different things in the same list. Because the epoch keeps pre-adoption commits out of the store
  entirely, the practical effect matches the design's intent; the difference would show only in a
  repository that ingested some pre-epoch history and not the rest.
* **CI persistence.** In CI the gate writes a manifest into a throwaway checkout nobody commits, so
  CI validates against a record it does not persist. Accepted deliberately: ingestion is
  idempotent, so nothing breaks, and the durable evidence store stays only as complete as local and
  orchestrated runs make it. The alternatives — CI committing to the repository, or an evidence
  store outside git — are worse.

## Adopted 2026-09-04

`.factory/trace-claims.yaml`'s `epoch` names the last commit on `main` predating any `SR:` trailer,
and `core.hooksPath` is set to `.githooks`, so commits are checked as they are written and
ingestion starts after the epoch instead of walking pre-adoption history.

Adoption surfaced one more defect worth recording, because it would have blocked all work rather
than checking anything: the hook shim ran `exec python -m coherence.register.claims`, and bare
`python` on the adopting machine resolved to a global miniconda with no `coherence` installed — so
the hook exited 1 on *every* commit. It now resolves the worktree's `.venv` first, then `uv run`,
and **warns and passes** when it finds neither. Failing open there is deliberate: a missing
interpreter is not evidence of a missing claim, and a hook that fails closed on its own environment
gets bypassed with `--no-verify` within the hour, taking the useful feedback with it. The real
check runs at ingestion time, where it cannot be skipped.
