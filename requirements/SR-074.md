Source: [[docs/superpowers/specs/2026-08-31-sr-code-validation-traceability-design.md#Canonical relation model|SR-to-code and validation traceability design]], rule 1 of the "Canonical relation model": *"`path` is repository-relative and must resolve inside the project."*

> Status: proposed; semantic adoption remains subject to the existing per-SR human consent workflow.

Authored 2026-09-17 with project-owner consent given in an interactive session, from the
optional-contract-artifacts plan. A contract catalog is untrusted input: it is authored text
that decides which files the compiler will read, hash and place in a dependency closure. The
existing repository discipline (feat17-planning-bootstrap design: every persisted path is a
repository-relative path below the selected project root, with absolute, drive, UNC, NUL,
traversal and reparse-point forms rejected) applies unchanged. This requirement deliberately
splits the two failure modes: **lexical** unsafety is decided on the declaration itself and
cannot be rescued by an in-root resolution, while **resolution** unsafety is decided on the
canonicalized target. Collapsing the two into one post-resolution check is the false green this
requirement exists to prevent.
