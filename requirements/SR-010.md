**Statement corrected during authoring (2026-09-03).** "underlined invariant kernel" was a typo;
the source anchor's own §4 uses "the invariant kernel" (line 204) and "Minimal invariant kernel"
(line 92), never "underlined", so the statement now reads "the invariant kernel", matching the
source's own §4 wording verbatim. No content or scope change: the four-value Requiredness enum and kernel rule
1's blocking behaviour (an execution error, missing executable, or invalid result cannot become
pass on a task's own justified SR) are unchanged, and both are fully backed by passing tests
(`substrate/policy/obligation.py`'s `Requiredness` literal; `coherence/measurement/pipeline.py`'s
own-SR-vs-swept-SR distinction).

AC-1 is proven by a new test written during this authoring pass,
`test_compile_obligations_requiredness_is_always_one_of_the_four_literal_values` -- no existing
test asserted the closed four-value set across scope kinds and presets in one place, so this adds
that direct proof rather than stretching a loosely-related candidate (the ambiguous-duplicate-SR
test `test_compile_obligations_duplicate_profiles_are_ambiguous_and_blocking` was considered and
rejected: it shows every kind pinned to `"blocking"` under one specific ambiguity condition, not
the closed-type claim). AC-1 deliberately does not state how many obligation *kinds* exist -- today's compiler produces
five (`ci_verification`, `task_justification`, `verification_result`, `human_review`,
`test_marker`), more than [[docs/superpowers/specs/2026-08-22-coherence-progressive-assurance-design|D16]]'s
design-time "three obligation kinds" figure, because later increments (documented in those
increments, not here) extended the same compiler function. That kind count is out of scope for
this SR's claim about the `Requiredness` type itself.
