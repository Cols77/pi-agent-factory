**Statement corrected during authoring consent (2026-09-03).** It originally also claimed "typed
lifecycle relationships (derives/decomposes/refines/allocates/implements/verifies/validates/evidences/corrects/impacts/supersedes)"
as something the system accepts and rejects-at-load for arbitrary node kinds. That half does not
exist: `coherence.trace.model.EdgeKind` (a `Literal[...]`) lists all twelve lifecycle-relationship
kind names -- derives/decomposes/refines/allocates/implements/verifies/validates/mitigates/evidences/corrects/impacts/supersedes,
where `mitigates` does double duty as both a lifecycle-relationship kind and a task-justification
kind -- but that is only a type-level enumeration used so the shared `Edge` dataclass can
represent a justification edge whose kind happens to be `corrects`/`implements`/etc. There is no
frontmatter field (a `relationships:` list or similar) on any non-task node kind that is parsed
into these edges, and no load-time rejection path for an unsupported relationship kind analogous to
`_justification_scope_error`/`InvalidJustificationError`. Grepping the codebase for
derives/decomposes/refines/allocates/verifies(edge)/validates(edge)/evidences/impacts turns up zero
occurrences outside that one `Literal` declaration. Design-doc §4 and D16 both frame the wider
vocabulary as schema-only, deferred ("declared in the schema but not compiled or tested until a
real use case needs them") -- not something FEAT-002's thin slice implements. The statement now
describes exactly what is implemented and tested: typed task justification on task nodes, with the
legacy `satisfies:` shorthand preserved, rejecting an unsupported kind or malformed entry at load.
The broader lifecycle-relationship vocabulary stays declared-only in `EdgeKind` until a real use
case drives a future SR to compile it -- that is new parsing/validation surface across every node
kind, not a small mechanical addition, so it is out of scope here (mirrors how [[SR-004]]'s AC-3
and [[SR-008]]'s AC-4/AC-5 were narrowed to what is automatable today during their own authoring
consent).

**AC split during authoring (2026-09-03).** The draft combined the trace-graph-edge behaviour and
the substrate-ledger-parsing behaviour into one criterion per topic, each pointing at two files at
once. Every existing acceptance criterion in this register binds to exactly one test file, so the
combined criteria are split by the module that actually proves each half: AC-1 (edges in
`coherence.trace.model`, proven by `tests/unit/trace/test_model_edges.py`) and AC-2 (typed
`Justification` parsing in `substrate.ledger.tasks`, proven by
`tests/unit/substrate/ledger/test_tasks_justification.py`) cover the accept path; AC-3 (scope_error
on the trace node) and AC-4 (`InvalidJustificationError` from the ledger) cover the two ways a
malformed or unsupported-kind entry is rejected at load. `test_model_nodes.py` had no test for the
multi-key-entry case that AC-3 needed (only the unsupported-kind case existed) -- added
`test_task_with_multi_key_justification_entry_degrades_to_a_scope_error`, mirroring the existing
`test_task_with_unsupported_justification_kind_degrades_to_a_scope_error`, against the
already-implemented `_justification_scope_error` check (`len(entry) != 1`) in
`src/coherence/trace/model.py` -- no production code changed for this AC.
