Source: [[docs/superpowers/specs/2026-09-05-per-criterion-measurement-seed|Per-criterion measurement
and complete verdicts — seed]].

Discovered while auditing why every "measured passing" verdict on disk traces back to an agent's
own transcription rather than a run. `verify_sr_marker` (`src/coherence/register/closure.py:129`)
does `has_marker = req.id in collect_markers(path)` — a static scan for a marker's *presence*,
never an outcome from executing anything. Only a `Binding` plus a harness produces a real pass/fail,
and checked directly against the whole register: no requirement declares `binding.harness` — all
seven bound SRs (`SR-001`–`SR-007`) carry `harness: null`. `coherence-measurement run --all`
(`select_requirement_ids` in `src/coherence/measurement/pipeline.py`) selects exactly those seven
and errors on every one of them identically (`"error": "binding: no harness named yet"`,
`src/coherence/measurement/report.py:64`), skipping the other 55 requirements entirely since none
carries a binding at all. Meanwhile every "measured passing" entry actually recorded in
`validation/validation-report.json` carries `"recorded_by": "agent"` in its own `provenance` block —
transcribed by hand from a command's console output, not emitted by any code in this repository.

**The granularity gap, not only the missing-harness gap.** `SimTestbenchHarness._run_pytest`
(`src/coherence/measurement/sim_harness.py:112`) already runs a pytest selection and already
computes `unit_pass_rate` from real JUnit XML output — this machinery exists and works. But
`binding.experiment` names exactly one file or node id, and the run is additionally scoped by a
bare marker name (`-m unit` by default, `pytest_marker` from `from_config`). `pyproject.toml`
registers `sr` as a marker that *takes an argument* (`pytest.mark.sr("SR-0001")`), and pytest's
`-m` expression language cannot select on a marker's argument value — confirmed no `conftest.py`
anywhere in this repository hooks `pytest_collection_modifyitems` to make that possible. So the
harness that exists today can measure "this file's tests passed," never "this requirement's own
acceptance criteria passed." Checked corpus-wide, not assumed: 51 of the register's 54
`acceptance[].verification.ref` entries name a bare file; only 3 name a pytest node id. A
requirement with three acceptance criteria bound to the same test file gets one pass rate for the
whole file today, never three individually addressable outcomes.

**The boundary — what this does not duplicate.** [[SR-002]] owns the register's closure state
machine (proposed / measured / declined); it is silent on how a measurement is computed, and
nothing here touches `classify`'s state transitions, only what feeds a `validation` result into
them. [[SR-024]] owns running harnesses and recording verdicts plus evidence manifests; it is
silent on granularity — nothing in its statement requires a verdict be per-criterion rather than
per-file. [[SR-059]] owns visibility and currency of human-consent criteria: a `human_review`-class
obligation's requiredness never silently dropping to `not_applicable`, and a recorded accept
decision going stale the moment its target's content changes. It already gestures at the rule
AC-3 needs — manual, agent-assisted review must be "as trackable and impossible to silently skip as
a passing automated check is" — but it states no closure consequence for a requirement that mixes
a `manual` criterion with measured ones, and nothing today enforces one. This requirement is the
one that states that consequence and ties it to per-criterion measurement rather than to a whole
requirement's aggregate state.

**Reusable parts, not a rebuild.** `coherence.register.relations._resolve_test` ([[SR-050]] T1) already
validates a `path::node::node` pytest node id against the code index and already rejects a line
number used as identity — exactly the per-criterion `ref` shape AC-2 needs resolved. `Binding`
already supplies the assertion threshold (`assert_expr` via `evaluate_assertion`), the
re-measurement cadence, and the checksum-staleness mechanism (`content_checksum` /
`is_checksum_current`) that today only the seven bound SRs get. `coherence register show` already
prints a `binding:` line (`src/coherence/register/cli.py:133`) exactly where a per-criterion pass
rate would read naturally — AC-4's surface already has a place to grow into.

**A named consequence, stated honestly.** On the day AC-3 is enforced, [[SR-050]] and [[SR-058]] — the
only two requirements mixing `manual` with `test_marker` criteria — stop being reported
measured-passing until a `review:<sr_id>` decision is recorded for each. No `review:<sr_id>`
decision exists anywhere in this repository today (`gate-decisions/` holds 15 files, all `sr:*`
authoring-consent, zero `review:*`), so this is not a hypothetical: enforcing AC-3 immediately
removes both from whatever count currently treats them as passing. That is the system reporting the
truth about its own remaining manual criteria, not a regression — [[SR-050]]'s own entry in
`validation/validation-report.json` already carries a hand-written `error` withholding its passing
verdict for this exact reason, predating that requirement's later acceptance-criteria changes; this
requirement would make that an enforced fact instead of something a transcribing agent has to
remember to keep saying by hand.

**Registered `manual` on all four criteria, honestly, not as a permanent excuse.** [[SR-057]] was
registered the same way — see its body's "Acceptance criteria added on review (2026-09-03)" note:
stating a testable behavioral claim before choosing an implementation detail is correct; using
`manual` to avoid ever choosing one is not. There is a mild, named self-reference here: a
requirement about not leaning on `manual` criteria forever is itself authored with four `manual`
criteria. The alternative considered and rejected — pointing each AC's `verification.ref` at a
`test_marker` naming a test file that does not exist yet — is worse, not more honest: it would make
`verify_sr_marker` (`src/coherence/register/closure.py`) emit a CONFIGURATION finding against this
very requirement on day one, reporting a false diagnostic about a missing marker rather than an
honest, reasoned statement that the capability does not exist yet. Each `reason` above names
exactly what already exists, what is still missing, and what converts it to `test_marker`.
