Source: docs/superpowers/specs/2026-08-22-coherence-progressive-assurance-design.md#4.

**Statement kept at the full source claim during human authoring consent (2026-09-03), reversing
an earlier narrowing.** An automated authoring pass had drafted a narrowed statement dropping
"status" and "inbox" as consumers, on the grounds that grepping `src/coherence` for
`compile_obligations`/`Obligation` usage confirms only three of the five exist today:
`coherence.navigate.health` (dimensions 4/5 and 11), `coherence.navigate.obligations` (the
navigator's effective-profile view, wired into `coherence.navigate.cli`), and
`coherence.policy.ci` (`required_ci_commands`). `status_snapshot` (`src/coherence/status.py`) and
`coherence register status` (`src/coherence/register/cli.py`) have zero references to obligations
or the compiler, and `list_items` (`src/coherence/inbox.py`) likewise never consumes a compiled
obligation.

**The human reviewing this SR held that the full five-consumer claim is the correct statement of
intent** (it matches the source design doc's §4 verbatim) and should not be narrowed away just
because two of the five consumers are not yet wired — narrowing the statement to match current
code would understate what this requirement is actually meant to guarantee. The statement is
therefore restored to the original five-consumer wording. AC-1..AC-5 below are unchanged: they
honestly cover only the three consumers (health, navigator, gates) that are implemented and tested
today, so the statement now claims more than its own acceptance criteria currently prove — that
gap is real, known, and tracked explicitly via a formal deferral (see below), not left implicit.

Wiring `status.py`'s probes and `inbox.py`'s `list_items` to the compiled obligation set is a real
design decision (which obligations surface in a status line or inbox item, at what requiredness
threshold, for which scope) that no increment in the design doc's own integration map (§10)
assigns: Increment 2C covers only CI/gates, 3B only the navigator, 5 only the health vector. This
requirement is formally deferred pending that follow-on work — see the `deferred` block in this
file's frontmatter and `gate-decisions/sr-SR-009.json` for the human decision record.

**AC-5 narrowed during adversarial review (2026-09-03).** It originally claimed CI's required
command list is built "only" from compiled `ci_verification`/`blocking` obligations and is "never
a hand-maintained step list," full stop. `src/coherence/policy/ci.py`'s `required_ci_commands`
contradicts that as literally written: after extending `commands` with the compiled obligations'
`resolve_cmd`s, it unconditionally appends two hardcoded strings, `"coherence trace check"` and
`"coherence register check"` — a real, if small, hand-maintained tail the bound test itself
(`test_includes_every_declared_gate_command_in_order_with_python_substituted`) already works
around by slicing `commands[:-2]` before asserting the compiled portion, and that a second,
unmarked test (`test_structural_checks_are_always_appended`) confirms is unconditional. Reworded
AC-5 to claim only what the code and test prove: the *gate* commands are exclusively
obligation-derived (never hand-maintained), and the two structural checks are a separate,
unconditional, non-obligation-derived tail. No test changed — the existing bound test already
supports the narrower claim; only the criterion text was corrected.
