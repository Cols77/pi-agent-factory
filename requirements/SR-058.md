Source: [[docs/superpowers/specs/2026-09-03-cross-feat-semantic-overlap-detection-seed|Cross-FEAT/SR semantic overlap detection at scale — seed]].

Discovered during [[SR-004]]'s authoring-consent decision (2026-09-03), alongside [[SR-057]]:
having found that SR-050 reuses [[SR-023]] and extends [[SR-049]] with no typed relation recording
either link, the human asked the broader question — at hundreds or thousands of SRs and FEATs, how
do you reliably catch overlap **nobody wrote down anywhere**, where neither requirement's author
knew about the other and so no prose mention exists for a mirror check to find? That is a
different detection problem from [[SR-057]]'s (which finds gaps between what was declared and what
was narrated): this one finds overlap between what was written and other things also written, with
no declared or narrated link between them at all. Kept as a separate SR from [[SR-057]]
deliberately — [[SR-057]]'s mechanism is deterministic and `test_marker`-able; this one is
necessarily similarity-based and needs a judgement call on every candidate, never a bare pass/fail.

**Acceptance criteria added on review (2026-09-03).** Earlier registered with zero ACs; corrected
for the same reason as [[SR-057]] — not having chosen the similarity mechanism's implementation
(embeddings vs. another technique, the exact threshold) is not a reason to avoid stating the
observable contract. AC-1/AC-2 above state that contract without committing to a mechanism, both
`manual` and honestly reasoned as unimplemented. The seed doc above still records technical recon
toward the eventual design — a two-layer shape (deterministic structural completeness, which is
[[SR-057]]'s territory, plus embedding-based candidate generation narrowed by an intersection with
SR-057's declared-relation data, verified by a model only on the surviving candidates, never
auto-applied) and an explicit "not required, SQLite if anything, never a second system of record"
answer to the storage/tech-stack question — but that recon is not binding, and where the
similarity threshold sits waits for someone to plan it against real corpus scale.

**AC-1 sharpened on review (2026-09-03).** The human's own framing: the whole point of scaled
overlap detection is to not rely on human review for the corpus-wide search itself (that's the
part that doesn't scale to hundreds or thousands of SRs) -- but that doesn't mean removing the
human from resolving a flagged overlap once found; it means the model does the searching and the
first-pass judgement, a human only sees what survives that judgement, and the human's resolution
is captured, not left to evaporate. The original AC-1 said "surfaced as a review finding," which
left both halves implicit: it didn't say the candidate is model-verified before a human ever sees
it (so the human's attention is spent only on real candidates, not raw similarity noise), and it
didn't say the human's resolution is recorded as anything more durable than the finding itself
being read. Restated to make both explicit, and pointed at reusing [[SR-050]]/AC-3's existing
human_review/DecisionFile mechanism rather than inventing a parallel one -- the same
"agent proposes, gate enforces attributed human consent" pattern already proven there.

**AC-1 (automated candidate detection) split out (2026-09-03).** The narrowing step -- turning a
corpus of N requirements into a bounded candidate set without evaluating all O(N^2) pairs -- was
only implicit inside the model-verification AC's `reason` text, never its own testable claim. It
is the part of this SR that most directly answers "how do you do this at scale" and deserves to be
verifiable on its own once built, independent of whether model-verification or the FEAT-017
integration exist yet. Split out as AC-1; the former AC-1 (model verification + human decision
capture) and AC-2 (FEAT-017 integration) renumbered to AC-2/AC-3.

**AC-1 + AC-2 built and closed `test_marker` (2026-09-04); AC-3 stays `manual`, deferred,
untouched.** Both mechanisms now exist end to end. AC-3 (wiring this into FEAT-017
PLANNING-BOOTSTRAP's authoring pipeline) was explicitly out of scope for this pass and is
untouched -- its `verification` block, `reason` text, and everything else about it are exactly as
they were before this work; nothing under this SR calls the new detector from any planning
workflow.

*AC-1 -- narrowing.* `coherence.register.overlap` (module docstring carries the full design
rationale) computes each SR's `SrVector` -- a bag-of-words term-frequency representation over its
`statement` + every `acceptance[].criterion` text, cached by `content_fingerprint` (a hash of
exactly that text) so a re-run only re-tokenizes SRs whose statement/acceptance text actually
changed (`compute_vectors`, persisted at `.factory/overlap-index/vectors.json` -- a derived,
disposable, rebuildable cache, gitignored, never a second system of record, mirroring
`.factory/code-index/`'s existing precedent per the seed doc's own storage answer). `_tfidf_weights`
computes fresh corpus-wide TF-IDF weights from those cached term-frequency vectors on every run
(deliberately NOT cached -- IDF depends on the whole corpus's current membership, and caching it
would silently stale the moment any other SR changed; this layer is cheap, an O(N) pass over
already-tokenized vectors, so recomputing it costs nothing the cache needed to save).
`generate_candidates` finds each SR's top-`k` cosine-nearest neighbours (`k` defaults to 10, per
the design), then intersects with `has_declared_relation` (checked from EITHER SR's `upstream` OR
`relates_to`, in EITHER direction, per SR-057's own "not necessarily declared from both sides" data
shape) to drop any pair that already carries a declared relation. Output is bounded at `O(N*k)`,
never the full `O(N^2)` pairwise set, regardless of corpus size or how uniformly similar it is --
`test_narrowing_stays_bounded_not_quadratic` proves this against a 60-SR fixture engineered as the
worst case (every pair maximally similar, none declared), asserting candidate count stays at or
under `N*k` and strictly under the `N*(N-1)/2` quadratic bound. `test_near_duplicate_pair_with_no_
declared_relation_is_surfaced`, `test_similar_but_declared_pair_is_excluded`, and
`test_dissimilar_and_undeclared_pair_never_becomes_candidate` prove the three-way narrowing
contract (similar+undeclared surfaces, similar+declared excludes, dissimilar+undeclared never
appears) the design's Layer-1 intersection describes. All in
`tests/unit/coherence/register/test_overlap.py`, bound via `@pytest.mark.sr("SR-058")`.

*AC-2 -- model verification + human decision capture.* `verify_candidates` hands each surviving
candidate to an injected `judge: Callable[[OverlapCandidate], dict]` (the same dependency-injection
shape as `coherence.register.fidelity.review_fidelity`'s `judge`) and classifies the result into
one of three DISTINCT statuses -- `"confirmed"`, `"dismissed"`, or `"unavailable"` -- never
conflating "the judge said no" with "the judge didn't run":
`test_verify_candidates_confirmed_and_dismissed_are_distinguished`,
`test_judge_unavailable_is_never_silently_no_overlap`, and
`test_judge_malformed_output_is_unavailable_not_dismissed` prove this. `run_overlap_check` (the
full AC-1→AC-2 pipeline) then builds a gate item ONLY for `"confirmed"` candidates -- item ids
shaped `overlap:<run_id>:candidate:<pair_id>`, exactly mirroring
`coherence.audit.runner._gate_item_ids`'s `coverage:<run_id>:proposal:<id>` shape -- and resolves
them through the EXISTING, unmodified `coherence.gate` mechanism
(`coherence.gate.service.resolve_gate` / `coherence.gate.store.write_decision`/`load_decision`;
`coherence.gate.model.ITEM_ID_PREFIXES` gained one new entry, `"overlap:"`, no other change to that
module's validation rules). `test_dismissed_candidate_never_produces_a_gate_item` proves a
genuinely-dismissed candidate never reaches a human (no gate item, no decision file expected) and
`test_confirmed_candidate_blocks_until_a_decision_is_authored` proves a confirmed one blocks
(`"blocked"` attended, `"blocked_unattended"` unattended) until one exists -- never auto-finalised,
matching `coherence.audit.runner.run`'s own gate discipline for its `coverage:<run_id>` gate.
`test_human_accept_decision_round_trips_through_decision_file` writes a real `DecisionFile`
(`accept`, with `reason` recording the relation a human judges the pair needs -- SR-058's own
"confirming ... the relation it needs" language, captured as information on the decision, never
auto-written into either SR's frontmatter) and re-runs the pipeline with the SAME `run_id`,
proving the gate resolves to `"accept"` and the decision round-trips byte-for-byte through the
real store; `test_human_reject_decision_requires_reason_per_existing_gate_rules` confirms
`reject`/`defer` still require a reason under the SAME, unmodified `DecisionFile` validation this
SR adds no new rule to. All in `tests/unit/coherence/register/test_overlap.py`.

The real, `PiAgentBackend`-dispatch judge is `coherence.audit.overlap_dispatch.default_judge`,
living under `coherence.audit` rather than `coherence.register` for the SAME layering reason T5
(SR-050) already established for `coherence.audit.fidelity_dispatch` --
`tests/unit/requirements/test_coherence_parity.py` statically forbids any file directly under
`src/coherence/register/*.py` from importing `factory.*`, even a function-local import, so
`coherence.register.overlap` only ever sees `judge` as an injected callable and never constructs a
real one itself. Dispatches a fresh, read-only, no-bash subagent under the new
`AgentRole.OVERLAP_REVIEW` (`src/factory/orchestrator/types.py`), loaded with the new
`.pi/skills/overlap-review/SKILL.md` (deliberately scoped, per its own text, to "is this a
plausible overlap", never "do these conflict" -- the overlap-only-not-conflict-detection scoping
call below). `coherence.cli._register_overlap_judge_factory` wires this real judge in for
`coherence register overlap-check`, mirroring `_register_judge_factory`'s existing fidelity
wiring exactly; a caller that bypasses that composition boundary (bare `coherence.register.cli`)
degrades to `_no_overlap_judge_configured`, which raises `OverlapJudgeUnavailable` -- every
candidate reports `unavailable`, never a silent pass, matching `_no_judge_configured`'s existing
precedent for fidelity.

*Why AC-2 is honestly `test_marker`-able (unlike SR-050/AC-4's comparable-looking clause).*
AC-4's criterion asked whether a specific finding on a REAL link is the product of a genuine
judgement -- a live, per-run, un-pin-downable claim no fixed test can prove, which is why it stayed
`manual` even fully built. AC-2's criterion makes a different, PROCEDURAL claim: that the PIPELINE
routes every candidate through model verification before any candidate becomes human-facing, and
that a human's resolution is captured as an attributed decision rather than a passive finding. That
is a claim about wiring and gating -- exactly the shape SR-050/AC-3's `human_review` mechanism
already proved `test_marker`-able with an injected/stubbed judge, and exactly what the tests above
exercise with hand-written `judge` callables rather than a real model call. This SR makes no claim,
anywhere, that a live model's verdict on a real requirement pair is always correct -- only that the
process around that verdict is sound, which is what is actually tested.

*Scoping judgement calls made while building this, stated explicitly (per the same discipline
SR-050's own closures used):*
- **Lexical, not real embeddings.** Per the approved design, `overlap.py`'s own module docstring
  states this is a deliberately simple v1 choice (TF-IDF-style bag-of-words cosine, pure Python, no
  new dependency), and flags upgrading to real embeddings or RAG-style retrieval as explicit,
  un-silent future work if recall proves insufficient at real corpus scale -- never presented as
  the final answer.
- **Overlap detection only, never conflict detection.** Matches the approved design's v1 scope
  exactly: `generate_candidates`/`verify_candidates` never attempt to distinguish "these two SRs
  conflict" from "these two SRs overlap" -- a candidate either looks like a plausible overlap or it
  doesn't, and `.pi/skills/overlap-review/SKILL.md` tells the judge the same scope limit.
  Distinguishing conflict from overlap is future work, not silently assumed here.
- **"The relation it needs" is captured, never auto-declared.** `OverlapVerification.suggested_
  relation` and a human's own `Decision.reason` are where this information lives; nothing in this
  SR's code ever writes to an SR's `upstream`/`relates_to` frontmatter. Matches the design's
  explicit "the model and this mechanism only ever produce a finding + a place for a human decision
  to land" rule.
- **Per-run gate scoping.** `overlap:<run_id>` gate decisions live under
  `<project_root>/overlap-reviews/<run_id>/gate-decisions/`, one decision file per run (mirroring
  `coherence.audit.runner`'s `coverage-reviews/<feat>-<run_id>` convention, including that
  directory's existing `.gitignore` treatment as regenerable scratch). This means a fresh `run_id`
  re-asks a human about a pair they already resolved in a prior run -- a known, inherited limitation
  of the exact pattern this SR was told to reuse rather than a new gap this SR introduces; resuming
  the SAME `run_id` (as every test above does) short-circuits correctly, same as coverage review's
  own resume semantics.
- **CLI surface.** `coherence register overlap-check` (`coherence/register/cli.py::
  cmd_overlap_check`), a standalone, manually-invoked command -- explicitly NOT wired into any
  planning pipeline. `--project-root`, `--run-id`, `--k`, `--unattended`, `--no-gates` mirror this
  repo's existing flag conventions for the sibling `review`/`check` commands.
