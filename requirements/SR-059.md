Source: [[docs/superpowers/specs/2026-09-03-manual-criteria-enforcement-seed|Manual criteria must not silently rot — seed]].

Discovered while splitting [[SR-050]]/AC-2 into AC-2 (structural + evidence-integrity, both
deterministic once built) and AC-4 (semantic fidelity, inherently a judgement call): pushing back
on "manual because unimplemented" surfaced that `_human_review_obligation`
(`src/coherence/policy/compiler.py`) compiles requiredness as `"blocking" if profile ==
"high_assurance" else "not_applicable"` — not a softer severity like [[SR-006]]'s accepted
`test_marker` graduation (`blocking`/`WARNING`), but literally not required at all outside
`high_assurance`. Under this repository's own default profile, a `manual` criterion's human review
is not merely easy to forget: nothing in the system asks for it. This is corpus-wide, not specific
to [[SR-050]] — every `manual`-kind acceptance criterion across every registered requirement is
affected identically.

**Acceptance criteria added on review (2026-09-03), same correction as [[SR-057]]/[[SR-058]].** No
longer zero-AC: AC-1/AC-2 state the observable contract (requiredness never silently
`not_applicable`; an accept decision never silently outlives the content it consented to) without
committing to a mechanism. The fix is not "eliminate manual review" — [[SR-050]]/AC-4 stays a
genuine judgement call by nature, however good tooling gets — it is making reliance on
agent-assisted review with human consent as trustworthy and unskippable as a passing automated
check, the way [[SR-050]]/AC-3 already proves is possible for one specific gate. AC-2 is no longer
hypothetical: presenting [[SR-057]] for its own decision demonstrated it directly (see AC-2's
reason). The seed doc records recon toward generalizing that proof: a possible new
`verification.kind` in the register schema and a staleness/expiry contract for review decisions —
not committed here.

**AC-1/AC-2 became `test_marker`-backed (2026-09-04).**

*AC-1 — profile-independent requiredness floor.* Grepped `compiler.py` for every `requiredness =`
assignment (per this task's own instruction, checked honestly rather than assumed): four exist.
`_task_justification_obligation` graduates `"blocking"`/`"advisory"` (never `not_applicable`);
`_verification_result_obligation` and `_test_marker_obligation` already graduate
`"blocking"`/`"required"` (never `not_applicable`); only `_human_review_obligation` had the exact
collapse this AC names — `"blocking" if profile == "high_assurance" else "not_applicable"`. That is
the ONE line changed: `"blocking" if profile == "high_assurance" else "required"`. `"required"` is
this repo's own existing vocabulary (confirmed by grep, same value `_verification_result_obligation`/
`_test_marker_obligation` already use under non-`high_assurance` profiles) — a level strictly between
`advisory` and `blocking`: visible, counted, non-gating outside `high_assurance`. Never
`not_applicable` for this gate kind under any profile, per the criterion's own words.
`test_compile_obligations_human_review_under_prototype_is_required_never_not_applicable` (renamed
from `..._is_not_applicable`, the exact prior-behavior test this AC falsifies) pins this;
`test_human_review_prototype_accept_is_satisfied_and_required` (renamed from
`..._but_not_applicable`) pins that a valid accept still satisfies the now-`required` obligation.
Both in `tests/unit/coherence/policy/test_compiler.py`.

*`inbox.py`'s `_authoring_consent_items` (the `sr:` authoring-consent surface AC-1 also names):
checked directly, as instructed, rather than assumed either way — it was ALREADY fine.* It carries
no `profile` parameter at all and never filters or grades any item by profile; every pending SR
surfaces as an inbox item unconditionally, under every profile, today and before this change. It had
no collapse to fix.

*Downstream consequence, found and fixed, not glossed over:* `coherence.navigate.health`'s dimension
11 (`human_review`) already filtered its obligation universe to
`o.requiredness in ("required", "blocking")` — written that way in anticipation of exactly this kind
of fix, per its own comment. Under the OLD `not_applicable` behavior, every non-`high_assurance` SR
was invisible to this filter; the moment `_human_review_obligation` started emitting `"required"`
instead, every SR (not only `high_assurance` ones) began participating in this dimension's
denominator — found only by running `tests/unit/coherence/test_health_dimensions.py` (outside this
SR's own narrow required list), which had two tests hard-coded to the old 3-SR-fixture count of 1
(only the `high_assurance` SR counted). Both updated to 3 (all three fixture SRs now count, none
satisfied, so `(0, 3, 0)`) with the reasoning stated inline — this is the CORRECT, intended
widening AC-1 exists to produce (prototype's human-review obligation becoming visible/counted, not a
side effect to suppress), not a regression to work around.

*AC-2 — content-checksum staleness.* A new module, `coherence.gate.content`
(`src/coherence/gate/content.py`), holds two functions: `artifact_content_checksum(path)` — a
`sha256:`-prefixed hash of the target file's raw bytes, deliberately broader than
`coherence.register.register.content_checksum` (which hashes only `statement`+`binding`, explicitly
excluding body prose, for a narrower measurement-binding-currency question) — and
`resolve_decision_currency(run_dir, decision_file, target_path)`, which compares a decision's stored
`content_checksum` against the target's current one. `DecisionFile` gained a new optional
`content_checksum: str = ""` field (`src/coherence/gate/model.py`), following the EXACT
`artifact_ref`/`decided_by` precedent named in this task's own brief: additive, `raw.get(...,
default)` in `from_dict`, **no `schema` bump** — every pre-existing `gate-decisions/*.json` file on
disk (this repo has several real ones) still loads correctly, the field defaulting to `""`.

Both real read sites this AC's criterion covers now call `resolve_decision_currency`:
`_human_review_obligation` (`compiler.py`, the `review:<sr_id>` gate) and `_authoring_consent_items`
(`inbox.py`, the `sr:<sr_id>` gate) — the two functions this task named, and the only two places in
`src/` that construct a `DecisionFile` for either gate kind at all (grepped: `write_decision`/
`DecisionFile(` has no OTHER production call site for `review:`/`sr:` gates — these decisions are
authored directly as JSON, by a human or an agent under human instruction, never through a CLI
command that could stamp the checksum at write time; stamping therefore happens at READ time, via
the migration path below, for every decision — old and new alike — the first time it's read after
this change). A checksum mismatch is treated exactly like a missing decision: `reviewed = False` /
the item stays pending — fail closed, never silently read as current. The exact SR-057 repro named
in AC-2's own prior `reason` text (editing `requirements/SR-057.md`'s statement/acceptance criteria
after its `sr:` accept decision was recorded, which used to leave that decision valid) is reproduced
directly, against the `review:` gate, as
`test_human_review_editing_sr_content_after_accept_reopens_obligation_sr057_repro` and, against the
`sr:` gate itself, as `test_editing_sr_content_after_authoring_consent_reopens_item`
(`tests/unit/coherence/test_inbox.py`) — both now correctly reopen.

**Migration/grandfathering, the deliberate judgement call named honestly, not glossed over (per this
task's own instruction).** This repo already has real `gate-decisions/*.json` files on disk
predating this feature (`sr-SR-001.json` through `sr-SR-058.json`, `sr-SR-048.json`, etc.), none
carrying a `content_checksum`. Treating a blank stored checksum as automatically stale would mass-
invalidate every already-granted consent across the whole repo the instant this ships, with no way
to know whether the covered content actually changed before or since — a worse failure mode than the
one this AC fixes. Instead, `resolve_decision_currency` GRANDFATHERS a checksum-less decision as
still-current for exactly one read, then immediately BACKFILLS the real checksum into the stored
file (via the existing, unmodified `coherence.gate.store.write_decision` — same validated, atomic
writer every other gate write already goes through, so the backfill can never persist something
`write_decision`'s own validation would reject) so any FUTURE content edit is correctly caught from
that point on. This is the one deliberate, documented exception to `inbox.py`'s previously-stated
"reads are side-effect free" contract — its module and function docstrings now say so explicitly,
and the exception is scoped as narrowly as possible: the backfill only ever rewrites the
machine-computed `content_checksum` field of an ALREADY-valid, already-recorded decision; it never
authors a new decision and never touches any decision's `action`/`reason`/attribution.
`test_resolve_decision_currency_backfill_does_not_create_a_permanent_loophole` and
`test_human_review_checksum_backfill_is_persisted_not_a_permanent_loophole`/
`test_preexisting_checksumless_authoring_consent_is_grandfathered_then_backfilled` prove the
migration path itself, not just its externally-observable effect: the checksum really lands on disk
(re-loaded and compared byte-for-byte), and a SECOND content edit AFTER the backfill is correctly
caught — proving grandfathering is a one-time migration, not a standing exemption a target could
keep exploiting. A backfill write that itself fails (e.g. a read-only filesystem) never raises past
`resolve_decision_currency` and never flips a read to "stale" — the grandfather still holds for that
one read (documented in the function's own docstring); it only means the next read grandfathers
again, which is safe (it can only ever err toward "still covers," identical to today's un-migrated
behavior), never toward wrongly reporting staleness.

**One adjacent surface deliberately left untouched, named honestly.**
`coherence.register.fidelity_persistence._accepted_review_decision_at` also reads a `review:<sr_id>`
DecisionFile (mirroring `_human_review_obligation`'s own scoping rules, per its own docstring) to
decide whether a stored fidelity finding should stop being re-escalated on re-run. It is explicitly
documented, in its own module, as "bookkeeping only... `_human_review_obligation` remains the sole
gate for [SR] closure" — never a gate itself. This task's approved design named exactly two read
sites to fix (`_human_review_obligation`, `_authoring_consent_items`); this third, adjacent,
non-gating consumer was not one of them and is not touched here. Its bookkeeping could, in principle,
keep treating a since-invalidated accept as still dispositioning a stale finding even after the real
gate (`_human_review_obligation`) has correctly reopened — a real, narrow gap, but out of this SR's
approved scope; a future SR could extend the same `resolve_decision_currency` call there.
