## 1. Context

The evidence-lifecycle work gives the factory durable manifests, freshness checks, reconciliation, recovery, and a shared Python-backed evidence model. What it does **not** yet give the human is a grounded place to ask:

- What is this feature or SR, exactly?
- What has been implemented and validated?
- Which decisions led here?
- What is fresh, stale, missing, or only partially supported?
- What can I trust in prose versus what is merely a projection?

`/review-plans` can read documents and the browser can show trace graphs, but neither produces a single, evidence-grounded system brief. The new `/system` navigator fills that gap.

This design is intentionally read-only. It does not create new evidence; it assembles a projection over recorded artifacts, derived aggregates, and synthesized text. The one write path is an explicit, user-initiated export (§4.5), and exported files are never readmitted as evidence.

## 2. Inherited constraints and approved decisions

> Items 1–6 are inherited from prior evidence-lifecycle and related specs (`2026-08-07`, `2026-08-03`, `2026-07-30`, `2026-07-27`, `2026-07-29`). Items 7–13 were answered directly by the user on 2026-08-07 in response to §12 and are binding. This document is **revised for approval**: implementation begins only when the user approves this revised design in writing.

1. **One model, many projections.** Python owns the data model and query logic. TypeScript only renders JSON results.
2. **No inferred provenance.** If a claim cannot be tied to recorded artifacts, it is shown as missing or degraded, never guessed.
3. **Recorded / derived / synthesized / missing stay distinct.** Every rendered field is labeled with its claim class.
4. **Synthesis must cite evidence.** Any natural-language paragraph must carry citations and a freshness state.
5. **Freshness is explicit.** A stale or partially missing dependency downgrades the claim; the browser never silently smooths it over.
6. **Feature and SR are scopes, not new sources of truth.** They are ways to slice the same repository evidence.
7. **A feature scope is a declared bundle.** A bundle is an authored file that names its members by exact ref. It declares **membership only**: it carries no claims, no status, and no rationale, and it is itself a recorded citation. See §3.3.
8. **The guide quotes; it never paraphrases.** Synthesized prose is fixed scaffolding plus verbatim spans copied from cited sources. See §4.4.
9. **Stale support collapses prose to bullets.** If any supporting dependency is not fresh, the paragraph is replaced by recorded bullets rather than shown with a warning.
10. **`/system` is opt-in.** It is not the default browser entry point. It is reachable from the browser during development sessions and directly via a registered command.
11. **Guides are ephemeral.** They are derived per request and never persisted as evidence. The only persistence is an explicit user-initiated export, and **an exported guide is never a citable source** (§4.5).
12. **Invocation is `python -m factory.system`.** There is no `factory` console script in this repo; every existing subpackage is invoked as a module.
13. **Plan checkboxes are not evidence of completion.** See §3.4.

## 3. Information model

### 3.1 Claim classes

| class | meaning | rendering rule |
|---|---|---|
| recorded | directly emitted by a canonical artifact or evidence file | show verbatim or lightly formatted, with citation |
| derived | deterministically computed from recorded inputs | show formula/result plus cited inputs |
| synthesized | scaffolding plus verbatim spans from recorded + derived data | show only with citations and freshness |
| missing | required information was not recorded | show as missing, never fill in prose |

> The **synthesized** class is produced by deterministic template assembly over recorded/derived inputs (see §4.4). It is not generated by a language model and never invents connective rationale between facts. Model-based synthesis is explicitly out of scope for this version; §14 records the deferred design so it can be added later without a rewrite.

### 3.2 Freshness states

Claim class and freshness are **orthogonal axes with one coupling rule**, not overlapping enums.

| state | meaning |
|---|---|
| fresh | cited inputs match the current recorded dependencies |
| stale | a cited input changed since the claim was recorded |
| degraded | the claim is only partially supportable; some supporting facts are missing or quarantined |
| n/a | the claim has no recorded basis to be current about |

**Coupling rule (schema-enforced):** `class == missing` if and only if `freshness == n/a`. Every other combination of the two axes is valid; these two values may not appear apart. `missing` is a claim class only and is not a freshness state; `degraded` is a freshness state only and is not a claim class. Task 1 tests assert both directions of the rule and reject the illegal cells.

Rules:
- synthesis may only use recorded or derived inputs;
- if any supporting dependency is not fresh, the synthesized paragraph is replaced by recorded bullets (§4.4);
- if nothing recorded supports the statement, it is missing, not synthesized.

### 3.3 Bundle declarations

A feature scope is a declared bundle. A bundle file:

- lists members as exact refs (`spec:`, `plan:`, `task:`, `sr:`) and nothing else;
- carries a human label and no other prose;
- **declares no status, no claims, and no rationale** — a bundle is an index, not an assertion;
- is itself a recorded citation, cited as the source of the membership list;
- is validated against a schema that rejects unknown fields, so narrative cannot be smuggled in.

When a bundle names a member that does not resolve, that member is reported `missing` and the bundle-level claims degrade. A missing member never removes itself silently from the brief.

Bundle files live in a declared directory resolved from repo config, alongside the existing register conventions. An absent bundle directory is a legitimate state, not an error: the loader returns no bundles and the scope list simply contains no bundle scopes. The navigator must never cite a path it has not resolved.

### 3.4 Plan checkboxes are not completion evidence

Plan documents in `docs/superpowers/plans/` use `- [ ]` / `- [x]` step tracking, and that state is **known-unreliable in this repository**: `2026-08-07-pif-browser-evidence-integration.md` carries 23 unchecked boxes while being fully implemented by commits `6b1778d` and `2ed6806`.

Therefore:

- checkbox state is **never** classified `recorded` evidence of implementation status;
- the navigator may display checkbox state only as `missing`, labeled as an unreliable signal, or omit it entirely;
- implementation status is sourced from the task ledger, evidence manifests, and validation reports — never from plan prose.

This rule exists because an unchecked box is the most tempting false signal in the tree: it is machine-readable, it looks authoritative, and it is routinely wrong.

## 4. User journeys

### 4.1 Feature briefing

1. User opens `/system` and selects a declared bundle.
2. The browser requests Python JSON for the briefing, matrix, timeline, and guide.
3. The brief shows:
   - scope identity and recorded source files, cited to the bundle declaration;
   - current implementation coverage;
   - validation coverage and freshness;
   - decision history;
   - a grounded prose summary.
4. Clicking a row jumps to the source artifact or manifest that backed it.

### 4.2 SR briefing

1. User selects an SR scope.
2. The brief shows the requirement statement, upstream links, binding, validation entries, stale status, and recent decisions.
3. If the SR has no binding or no validation, the view says so explicitly.
4. If the validation report is stale or missing, the guide collapses to bullets rather than inventing pass/fail confidence.

SR refs resolve through the existing requirements register loader (`factory.requirements.register`), which globs `SR-*.md` from a configured directory. The navigator must not hardcode a requirements path.

### 4.3 Decision timeline

1. User opens the timeline tab for a bundle or SR.
2. The browser lists recorded decisions in chronological order.
3. Each entry carries a citation and the claim class.
4. If timestamps are absent or incomplete, ordering falls back to recorded sequence numbers with a visible warning.

Actors, actions, and chronology are taken **only** from explicit records (signed review decisions, run journals, validation artifacts, manifests). Where a source record does not name an actor, the entry is labeled `unknown`/`not-recorded` — never guessed — and the event is marked `missing`/`degraded`. Timeline ordering is derived only from recorded timestamps or sequence numbers, never inferred from content or rationale.

### 4.4 Grounded natural-language guide

1. User opens the guide tab.
2. The browser renders a concise narrative split into short paragraphs.
3. Each paragraph carries citations and a freshness badge.
4. When any supporting dependency is not fresh, the paragraph is replaced by recorded bullets.

**Quotation, not paraphrase.** A synthesized paragraph is fixed scaffolding sentences plus **verbatim spans** copied character-for-character from cited sources. The guide never rewords recorded text. This is a testability decision as much as a fidelity one: a verbatim span can be verified by substring containment against its cited source, whereas a paraphrase cannot be checked for faithfulness without a model. Every quoted span carries the citation it was copied from, and Task 4 asserts containment for each span.

**Collapse predicate.** Prose selection is a single binary:

```
all_dependencies_fresh(paragraph) -> render prose
otherwise                         -> render recorded bullets
```

There is no graduated conservatism, no partially-hedged prose, and no stale-but-visible paragraph. One predicate, one test axis.

Synthesis is **deterministic template assembly**: the guide selects and fills predefined templates over recorded/derived inputs. It does **not** invoke a language model, and it never invents connective rationale between facts.

### 4.5 Guide export

Guides are ephemeral by default — computed per request, never written, never stored as evidence.

The single exception is an explicit, user-initiated export:

```text
python -m factory.system guide --scope <ref> --export <path>
```

An exported guide:

- is an **output artifact, not evidence**;
- records its generation timestamp and the full citation set it was built from;
- carries a header stating it is a point-in-time projection and not a source of truth;
- is written outside any evidence or manifest directory.

**Non-readmission rule:** the navigator must refuse to resolve a scope ref that points at an exported guide, and must never accept an exported guide as a citation source. Without this rule a synthesized guide becomes a "recorded" input to the next guide, and the whole claim-class discipline leaks in a single hop. Task 4 tests this refusal explicitly.

## 5. Python-owned query/model extensions

Add a small `factory.system` Python package that composes existing loaders from:

- trace graph / artifact relationships (`factory.trace`);
- requirements register (`factory.requirements.register`);
- evidence manifests and run journals (`factory.evidence`);
- validation reports (`factory.trace.validation_status`, `factory.validation`);
- review-guide and decision artifacts;
- task ledger and status data.

The package ships `__init__.py`, `cli.py`, and `__main__.py`, matching every existing subpackage.

### 5.1 CLI surface

```text
python -m factory.system brief    --scope <ref> --json
python -m factory.system matrix   --scope <ref> --json
python -m factory.system timeline --scope <ref> --json
python -m factory.system guide    --scope <ref> --json [--export <path>]
python -m factory.system scope    --json
```

There is no `factory` console script in this repo (`pyproject.toml` declares no `[project.scripts]`), and TypeScript already invokes Python this way — `trace-cli.ts:75` builds `uv run python -m factory.trace`. The navigator follows that convention exactly.

Scope references are exact, not fuzzy:
- `spec:<path>`
- `plan:<path>`
- `task:<id>`
- `sr:<id>`
- `bundle:<id>`

### 5.2 Query responsibilities

- **brief** — one-page summary for the selected scope.
- **matrix** — implementation/validation/decision matrix for the selected scope.
- **timeline** — chronological decisions and state changes.
- **guide** — grounded prose assembled from the other queries via deterministic template assembly (not a model).
- **scope** — list valid, declared scopes the browser can open, including declared bundles.

### 5.3 Model extensions

The Python model should expose stable dataclasses such as:

- `SystemScopeRef`
- `SystemCitation`
- `SystemClaim`
- `BundleDeclaration`
- `ValidationMatrixRow`
- `DecisionTimelineEvent`
- `SystemGuide`
- `FreshnessState`

Each record must carry enough metadata to explain where it came from and whether it is current.

## 6. Browser and PIF projections

### 6.1 Browser routes

- `GET /system` — landing page and scope picker.
- `GET /system?scope=<ref>` — default briefing view.
- `GET /api/system/brief?scope=<ref>`
- `GET /api/system/matrix?scope=<ref>`
- `GET /api/system/timeline?scope=<ref>`
- `GET /api/system/guide?scope=<ref>`

The browser does not recompute freshness, ordering, or citations. It renders Python JSON and nothing more.

### 6.2 PIF tools — extend, do not fork

`pi-ext/factory-watch/src/system-context-tools.ts` already exists and already registers the read-only tools `system_context`, `implementation_history`, `validation_status`, and `evidence_health` over `trace-cli.ts` and `evidence-client.ts`. `trace-tools.ts` is a second existing registration surface.

The navigator **extends `system-context-tools.ts`** with the new `factory.system` queries. It does not create a parallel client. A third registration surface over the same data would violate the constraint that browser/PIF code must not duplicate query, freshness, or provenance logic, and would give two code paths the chance to disagree about freshness.

The subprocess shim for `factory.system` follows the existing `trace-cli.ts` shape (`spawnSync`, `CliResult<T>`, JSON in / JSON out) and holds no reasoning of its own.

### 6.3 Rendering rules

- recorded rows get a neutral badge;
- derived rows show their inputs and algorithm label;
- synthesized prose shows citations inline or in a footnote rail;
- missing rows render plainly and do not get hidden;
- stale/degraded claims are visible and color-coded, but also text-labeled.

### 6.4 Entry points

`/system` is opt-in and does not replace the default browser landing page. It is reachable two ways:

1. from the browser during development sessions, as an explicit navigation target;
2. directly via a registered command, so the navigator can be opened without going through the docs browser first.

Command registration is an explicit implementation step with its own test, not a side effect of adding routes.

## 7. Schemas and interfaces

### 7.1 Top-level response shape

```jsonc
{
  "scope": { "kind": "bundle", "ref": "bundle:evidence-lifecycle", "label": "..." },
  "brief": { /* SystemClaim[] */ },
  "matrix": { /* ValidationMatrixRow[] */ },
  "timeline": { /* DecisionTimelineEvent[] */ },
  "guide": { /* SystemGuide */ },
  "freshness": { "state": "fresh|stale|degraded|n/a", "details": [] }
}
```

### 7.2 Shared record fields

```jsonc
{
  "kind": "recorded|derived|synthesized|missing",
  "text": "...",
  "spans": [
    { "text": "verbatim copied text", "citation_index": 0 }
  ],
  "citations": [
    { "kind": "manifest|task|requirement|validation|review|decision|trace|bundle", "path": "...", "sha256": "...", "anchor": "..." }
  ],
  "freshness": {
    "state": "fresh|stale|degraded|n/a",
    "reason": "...",
    "dependencies": [{ "name": "...", "expected": "...", "actual": "..." }]
  }
}
```

`spans` is present only on `synthesized` records and holds the verbatim quoted text with the citation it was copied from. The coupling rule from §3.2 is enforced here: `kind: "missing"` requires `freshness.state: "n/a"`, and `freshness.state: "n/a"` requires `kind: "missing"`.

### 7.3 Matrix row shape

```jsonc
{
  "subject": { "kind": "sr|task|validation|decision", "ref": "..." },
  "status": "passed|failed|error|blocked|never-run",
  "evidence": ["..."],
  "freshness": { "state": "fresh|stale|degraded|n/a", "...": "..." },
  "summary": "..."
}
```

`status` carries the recorded outcome only. Staleness and absence live on the `freshness` object, not in the status enum — the previous shape had `stale` and `missing` in both places, which let one row assert two different things about the same fact.

### 7.4 Timeline event shape

> Timeline events are sourced only from explicit records. `actor` and `action` are `unknown`/`not-recorded` when not stated by a source record; any event lacking actor, action, or timestamp is marked `missing`/`degraded` rather than inferred. `at` ordering comes only from recorded timestamps or recorded sequence numbers.

```jsonc
{
  "at": "2026-08-08T12:00:00Z",
  "actor": "human|dev|review|validation|orchestrator|unknown|not-recorded",
  "action": "approved|rejected|validated|repaired|published|stopped|not-recorded",
  "subject": { "kind": "task|sr|run|manifest", "ref": "..." },
  "citation": { ... },
  "freshness": { ... }
}
```

## 8. Failure handling

- Missing task, manifest, or validation files degrade only the affected scope.
- Corrupt evidence manifests are quarantined from the navigator and reported as missing/degraded.
- A bundle member that does not resolve is reported `missing`; the bundle degrades but still renders.
- A stale or partially missing timeline keeps its recorded events and marks the gaps.
- If synthesis fails, the browser falls back to the brief + matrix + timeline views with no prose guide.
- If a scope cannot be resolved exactly, the browser reports that fact and shows the scope picker again.

There is **no derived index and no cache**. Projections are computed on demand. The previous draft said a stale derived index would be "rebuilt automatically", which is a write and contradicts the read-only stance in §1; no implementation step ever existed for it. Compute-on-demand keeps the navigator honestly read-only.

## 9. Security

- All paths stay confined to the current repo root.
- The browser serves only recorded references or derived views of them; it never serves arbitrary object hashes.
- Generated prose must be HTML-escaped before rendering.
- Secrets in logs, transcripts, or blobs are not echoed into synthesized text unless an upstream redaction step already made them safe.
- The guide must not cite an unseen artifact by guessing its path.
- Export paths are validated and confined; exported guides are written outside evidence directories and are never readmitted as citations (§4.5).

## 10. Testing strategy

> **Marker discipline.** `pyproject.toml` sets `addopts = "-m unit"`, so any command that names an integration path without selecting the marker collects **zero tests and reports success**. Verified: `uv run pytest tests/integration -q --collect-only` → "No tests collected". Integration commands must pass `-m 'unit or integration'`, and `integration` must be added to the declared `markers` list. A gate that green-lights on an empty collection is the exact silent failure this factory exists to prevent.

### Python unit tests

- scope resolution from exact refs, including `bundle:`
- bundle declarations reject status/claims/rationale fields
- unresolvable bundle members report missing and degrade the bundle
- brief/matrix/timeline/guide shape validation
- the §3.2 coupling rule holds in both directions; illegal class/freshness cells are rejected
- freshness propagation for stale, degraded, and missing inputs
- citation retention and ordering
- fallback behavior when a source artifact is absent or corrupt
- plan checkbox state is never classified `recorded`
- no fuzzy matching, no inferred provenance
- no model-based synthesis; the guide is deterministic template assembly

### Python integration tests

- temp repo with a bundle, spec, SR, task, validation report, and decision artifacts
- stale validation after a content change collapses the guide to bullets
- missing manifest or missing blob degrades only that scope
- every synthesized span appears verbatim in its cited source
- export writes the citation set and timestamp; re-citing an exported guide is refused

### TypeScript tests

- `/system` route selection and scope picker
- command registration opens the navigator without the docs browser
- render labels for recorded/derived/synthesized/missing claims
- stale/degraded badges and inline citations
- exact command invocation is `uv run python -m factory.system ...`
- failure fallback when the Python CLI returns structured errors

## 12. Resolved decisions

The five questions previously open here were answered by the user on 2026-08-07:

1. **Root scope for a feature briefing** → a declared bundle (§3.3).
2. **May the guide paraphrase?** → No. Verbatim spans with citations only, chosen for testability as much as fidelity (§4.4).
3. **Stale supporting evidence** → collapse to recorded bullets; no warned-but-visible prose (§4.4).
4. **Default entry point?** → No. `/system` is opt-in, reachable from the browser in dev sessions and via a registered command (§6.4).
5. **Persist guide snapshots?** → No. Ephemeral, with explicit export only, and exports are never citable (§4.5).

Two implementation questions were also settled: invocation is `python -m factory.system` (§5.1), and the PIF surface extends `system-context-tools.ts` rather than forking a new client (§6.2).

## 13. Non-goals

- No editing UI.
- No new provenance inference.
- No browser-side freshness logic.
- No derived index or cache.
- No remote backend, auth, or cloud storage.
- No model-based synthesis in this version (§14).
- No auto-approval or auto-resolution of conflicts.
- No replacement for `/review-plans` or the trace/requirements tools.

## 14. Deferred: extractive synthesis

Deterministic template assembly reliably produces the least readable prose in the system, and readability is the guide tab's entire purpose. This version accepts that trade to guarantee no invented rationale.

A future version can recover readability without giving up determinism, via **extractive** synthesis: a model may only select and order recorded spans, and the output is post-validated by asserting every emitted span appears verbatim in a cited source — failing that assertion falls back to bullets. That is a deterministic verifier wrapped around a non-deterministic writer.

Nothing in this version should foreclose it. The `spans` field in §7.2 and the containment assertion in §10 are exactly the verifier interface such a change would need, so extractive synthesis can be added later behind separate approval without reshaping the model.
