# T-7 report — Generated wikilink mirrors (D-P8)

## Summary

The `## Related requirements` block in every `docs/features/FEAT-*.md` dossier is now
generated output: derived from the dossier's own `requirements:` frontmatter (cross-checked
against the trace graph's `contains` edges for that feature node), stamped with a
`sha256_bytes`-computed fingerprint, marked *derived — do not edit*, and enforced by
`coherence mirrors check`, which fails deterministically on any divergence and names the
offending file. All 20 dossiers were regenerated. FEAT-006's `![[SR-019]]` embed (NC-D) is now
`[[SR-019]]`, produced by regeneration — the line was never hand-edited. Reintroducing the
embed by hand and running the check fails it; regenerating restores it and the check passes
again.

## Where the code lives

New package `src/coherence/mirrors/` (peer of `coherence.trace`, `coherence.register`, etc.
— same `cli.py` + `__main__.py` + `generate.py` shape those packages use):

- `src/coherence/mirrors/render.py` — pure, I/O-free rendering of the block text and its
  fingerprint from an ordered SR id list. No filesystem, no frontmatter parsing, no trace
  graph — a small function that is trivially exhaustively testable.
- `src/coherence/mirrors/generate.py` — file-level regenerate/check logic: locates the block
  inside a dossier, derives the canonical id list from frontmatter (cross-checked against the
  trace graph), rebuilds the document, and either writes it (`regenerate_file`/`regenerate_all`)
  or raises on mismatch (`check_file`/`check_all`).
- `src/coherence/mirrors/cli.py` + `__main__.py` — `coherence mirrors generate` /
  `coherence mirrors check`, wired into `src/coherence/cli.py`'s `GROUPS` dict exactly the way
  `trace`/`register`/etc. already are (two-line diff: one import, one dict entry).

No import of `factory` anywhere in the new code (NC-A is not touched or extended).
`src/coherence/navigate/health.py`, `src/coherence/policy/compiler.py`, and
`src/coherence/register/closure.py` were **not modified**.

## Block format

```markdown
## Related requirements

<!-- derived — generated by `coherence mirrors generate`; do not edit -->
<!-- fingerprint: sha256:e9aec905ec56bf60ac4aaa61a0f8cb6815ebb3d4bc95b5ebfb3fe494b3242c3b -->
- [[SR-019]]
- [[SR-020]]
- [[SR-021]]
- [[SR-022]]
```

- **Marker** (`<!-- derived — generated by ... ; do not edit -->`): the human-facing "do not
  hand-edit" signal from the task brief, item 3.
- **Fingerprint** (`<!-- fingerprint: sha256:... -->`): `sha256_bytes` (reused, not
  reimplemented — `src/coherence/mirrors/render.py` imports it directly from
  `substrate.freshness.fingerprint`, the same helper `coherence.audit.observations` and
  `coherence.measurement.observations` already use) over
  `json.dumps(list(requirement_ids), separators=(",", ":"))`. Order-sensitive and
  content-sensitive by construction.
- **Entries**: `- [[SR-###]]` per id, in frontmatter order — never `![[...]]`.
- **Empty state**: `requirements: []` renders the exact pre-existing placeholder line,
  `- None yet; requirements are pending human-approved authoring.`, verbatim (constant
  `PLACEHOLDER_LINE`, reused, never re-derived from a template string that could drift).
- Everything is CRLF (`\r\n`) throughout, matching every `docs/features/FEAT-*.md` file on disk
  (verified: all 20 use CRLF exclusively, no bare LF). The block is read and written via
  `path.read_bytes()/write_bytes()` rather than `Path.read_text()/write_text()`, specifically
  to avoid Python's universal-newline translation silently turning every CRLF into LF.

**Only the entry-list run is rewritten.** The block locator (`_BLOCK_START_RE` +
`_CONSUMABLE_LINE_RE` in `generate.py`) matches the heading, its one blank line, then a
contiguous run of "generated-shaped" lines (HTML-comment marker/fingerprint lines, and any
`- ...` list item — covering both a plain hand-authored entry and this generator's own
marker+entry lines). The first line that isn't one of those ends the block; everything from
there to EOF is preserved byte-for-byte and re-appended after the freshly rendered block. This
was not a hypothetical concern — see "Self-review findings" below; it is exactly what protects
FEAT-017.md's real trailing prose sentence.

## How the check is wired

Followed the `coherence trace check` / `coherence register check` pattern in
`src/coherence/register/cli.py::main()` exactly: a `check_all(root) -> (text, exit_code)`
function, an argparse subcommand `check` under a new top-level group, wired into
`coherence.cli.GROUPS`. No `--json` flag (matching `coherence trace check`, per the task note).

Invocation:
```
coherence mirrors check --project-root .      # read-only, exits 1 on divergence
coherence mirrors generate --project-root .   # regenerates every dossier, idempotent
```
(also runnable as `python -m coherence.mirrors check|generate`, and `python -m coherence mirrors ...`)

# Fix report — review round 2

## Root cause, per the review

The locator inferred what it owned from line *shape* (does this look like "- ..." or a
comment?) rather than from an owned boundary. That produced two content-loss bugs (a
hand-authored bullet placed directly after the entry list with no blank line; a block ending
the file with no trailing newline), a CRLF-only crash that aborted the whole run instead of
failing one file, and a class of code the report's self-review pass never exercised (the
format-error path through `check_all`).

## Structural fix

**One change, not three patches**, per the review's own framing:

`src/coherence/mirrors/render.py` now emits an explicit **end sentinel**, `<!-- end derived -->`,
after the entry list, paired with the existing start marker. The generated block is now:

```markdown
## Related requirements

<!-- derived — generated by `coherence mirrors generate`; do not edit -->
<!-- fingerprint: sha256:... -->
- [[SR-019]]
- [[SR-020]]
- [[SR-021]]
- [[SR-022]]
<!-- end derived -->
```

`render_related_requirements_block` also now takes an `eol` parameter (default `"\r\n"`), so the
line ending is a caller-supplied fact, never assumed.

`src/coherence/mirrors/generate.py`'s `_locate_block` (returning `(start, end)` offsets) is a
single function with two paths:

1. **Owned-boundary path (steady state).** Search the document for the end sentinel line,
   anchored to line-start, after the heading+blank-line. If found, the owned span is
   *everything* between the heading and that sentinel, unconditionally — regardless of what is
   between them (a hand-tampered embed, a reordered entry, anything). This is what makes
   `![[SR-019]]` reintroduced between the markers still a divergence, and what makes a
   hand-authored bullet placed right after the entry list untouchable *once the file already
   carries the sentinel* — there is no shape question left to ask.
2. **Bootstrap path** (a dossier that has never been generated — all 20 real dossiers, once, on
   this round's first run against them; and any dossier that carries the old pre-sentinel V1
   format from the previous round). No sentinel exists yet, so the boundary has to be *derived*
   once. This path still steps line by line, but the per-line pattern is now strict: only this
   generator's own comment lines (`<!-- ... -->`) and lines that are an actual
   `- [[SR-...]]` / `- ![[SR-...]]` wikilink or the exact placeholder text match. A plain
   hand-authored bullet like `- Note: also relates to legacy system X.` does not match either
   pattern and correctly ends the run — this is what fixes Critical 1 (it is not "requires a
   blank line," which the review offered as an alternative but which would not actually have
   fixed the adjacent-bullet case; the fix is that the pattern is about *entry shape*, not
   *bullet shape*).

Every regex in the module now accepts `\r\n`, bare `\n`, or `\Z` (absolute end of string, i.e.
"this line has no trailing newline because the file/span ends here") as its line terminator —
this is what fixes Critical 2. `_detect_eol(text)` reads the file's own dominant line ending
(CRLF if any `\r\n` appears, else LF, else the repo default for a file with no newline at all)
once per file, and that is the `eol` passed to `render_related_requirements_block` — a file's
line-ending convention is read, never assumed or silently rewritten.

`MirrorFormatError` and `MirrorDivergenceError` stay two distinct exception types (a malformed
document vs. a well-formed-but-diverged one are genuinely different conditions worth
distinguishing in code), but `regenerate_all` and `check_all` now both catch `MirrorFormatError`
per node and continue to the next one — this fixes Critical 3. `regenerate_all`'s
`FeatureMirrorResult` gained an `error: str | None = None` field: a malformed dossier is
reported (`changed=False`, `error` set, file left completely untouched — no partial write) and
the loop moves on. `check_all` folds `MirrorFormatError` into the same per-file error list as
`MirrorDivergenceError`, so a malformed file shows up in the failing-check output exactly like
a diverged one, naming the file, and every other file in the tree is still checked.

`cli.py`'s `cmd_generate` was updated to surface `regenerate_all`'s new per-file errors (and
`coherence mirrors generate` now returns exit code 1 if any dossier could not be regenerated,
where it previously always returned 0).

## Design choice for Important 3 (LF-only files)

**Processed correctly, not rejected.** `_detect_eol` treats a file's own dominant line ending as
a fact to read and reproduce, the same way this module already treated CRLF as a fact to
preserve in round 1 rather than silently converting to LF. Rejecting LF-only files outright
would have been the easy option, but it would leave the generator CRLF-only-by-omission on any
checkout that uses `core.autocrlf=input` or is cloned on Linux/macOS — exactly the failure mode
the review reproduced. `test_an_lf_only_file_is_processed_correctly_and_stays_lf` asserts the
regenerated file contains zero `\r` bytes and that the check subsequently passes.
